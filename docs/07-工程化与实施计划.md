## 0. 怎么读这份文档（省 token 的硬规则）

文档总量约 25 万字符（约 20 万 token），`06` 一份就占一半。**任何一次对话都不通读文档**，按下面的顺序只读需要的部分：

1. `CLAUDE.md` 每次自动加载；设计规则和编码规则在 `.claude/rules/` 里，按改动的目录自动加载。
2. 新对话先读本文 §9（交接栏 + 任务台账）：`python3 scripts/doc-section.py 07 9`。
3. 按当前任务的「需读」列读章节：`python3 scripts/doc-section.py 06 3.6 2.12`。不知道章节号时先列目录：`python3 scripts/doc-section.py 06`。
4. **已经实现的部分读代码，不读文档**。`06` 某节实现后，标题下会有一行 `> 实现：<路径>`，直接去读类型、接口定义和测试。
5. 查「这个方向有没有被否掉」用 `grep -n 关键词 docs/02-决策记录与禁区.md`，不通读 `02`。
6. 不读生成物：`index.html`、`reference/src/**`、`openapi.json`、`pnpm-lock.yaml`、历史迁移 SQL（只看最新一个）。
7. 命令输出长时用 `tail`、`grep` 截取；大文件先看导出和类型，不整份 `cat`。
8. 一次对话尽量只推进一个任务；结束前（或上下文快满时）更新 §9 交接栏，下一次对话从交接栏接着做。

## 2. 仓库结构（单仓）

### 2.1 为什么设计和代码放一个仓

- 一个提交能同时改代码、`06` 和本文的台账，审查时一眼看出代码和文档是否一致（`06` §13.3 第 5 条）。
- 前端直接引用 `tokens/theme.css`，只有一份来源，不需要同步脚本。
- 代价：仓库历史已有 1.3 GB（PNG 反复重出）。本地无影响；CI 用浅克隆；以后把 PNG 迁到 Git LFS（§11）。

### 2.2 目录

```text
│   ├── bot-executor/    Bot 执行器（不连数据库，只走 RunnerTransport）
│   ├── llm-proxy/       模型代理（只监听本机 Unix Socket）
│   ├── desktop/         Electron 外壳（U2 才建）
│   └── web/             M2 的 /admin（先不建）
├── packages/
│   ├── core-protocol/   契约：TypeBox 定义、UI Block、RunnerTransport、AgentRuntimePlugin
```

### 2.3 依赖边界（自定义 ESLint 规则 `cc/boundaries` 强制，第一天就开）

> 实现：`tools/eslint-rules/index.js`。不用 `eslint-plugin-boundaries`：它靠导入解析判断目标，解析不到的引用（如没在 `package.json` 声明就直接 import 的包）会被静默放过；按包名和目录直接判断更可靠，规则不到 100 行。

| 谁 | 可以依赖 | 禁止 |
|---|---|---|
| `apps/*` | `packages/*` | `plugins/*` 的静态 import（插件只由启动装配处的 `PluginRegistry` 按配置加载） |
| `packages/*` | 其他 `packages/*`（不能成环） | `apps/*`、`plugins/*` |
| `packages/ui-kit`、`workbench-ui`、`admin-ui` | 浏览器 API、`core-protocol`、`ui-kit` | Node 内置模块；宿主能力只能经 `HostPlatformAdapter` |
| `plugins/*` | `packages/core-protocol`、`packages/mcp-tool-host` | `apps/*`、其他插件 |
| `sim` | 只依赖第三方库 | **任何产品代码**（不能共用产品的类型，否则契约对不上时测不出来） |
| 全部代码 | — | `if (engine === 'pi')` 这类按插件名分支（`06` §11.4） |

### 2.4 复用优先，不重复造轮子

- **先找再写**：新增工具函数、组件、类型前，先在 `packages/*` 里搜有没有现成的；有就用，不够就扩展它，不另起一份。
- **界面直接复用设计稿的样式**：`ui-kit` 直接引用 `tokens/theme.css` 和 `tokens/components.css` 的 `.cc-*` 类，React 组件只是给这些类包一层，不重写样式；外壳布局参照 `reference/src/v5/pc.css`。
- **成熟的库优先于自己实现**：日期、校验、表格、拖拽、画布、滚动条这类通用能力用社区成熟方案（`06` 已选定的直接用，如画布用 `@xyflow/react`、滚动条用 Radix ScrollArea）。只有 `06` 明确要自己做的（如 `advance()` 编排）才自己写。
- **同一件事只有一处实现**：前后端共用的类型和校验只在 `core-protocol` 定义；各连接器共用的重试、退避、分页放在共享包里，不在每个插件里各写一遍。

### 2.5 界面严格按定稿图实现

- 界面以 `reference/images/` 的定稿图和 `01` 的规范为准，布局、间距、字号、颜色、圆角、图标、文案都照图做，不自行发挥。
- 定稿图里没有的状态或页面（如某个报错态），先停下来补设计图、经用户确认后再写代码，不在代码里临时编一个样子。
- 每个界面任务交付时附界面对照截图（实际页面和定稿图并排，亮暗各一张），差异要么修掉，要么在验收单里说明原因。

### 3.2 生成链（单一来源，生成物提交进仓库）

```text
TypeBox 定义（core-protocol）→ Fastify 路由 → openapi.json（3.0.3）→ TS 客户端（以后再生成 Dart）
Drizzle 表定义 + 建表助手 → 迁移 SQL（含 RLS 策略、迁移账号与运行账号分离）
tokens/theme.css → packages/ui-kit 直接引用（以后生成 Dart 常量）
界面文案 → i18n/zh-CN.json 词条（06 §13.6 第 9 项，第一天就走词条）
```

`pnpm gen` 重新生成全部；`pnpm verify` 检查生成物是否最新，不最新就失败。

### 3.3 `pnpm verify`（本地就是 CI）

依次执行：类型检查 → 代码检查与依赖边界 → 生成物是否最新 → 单元测试 → 集成测试（真实 PG + 模拟服务）→ 端到端冒烟（P4 起）→ 改了设计文件时追加 `python3 scripts/build-all.py --check`。

- 目标耗时 3 分钟以内；超过就拆出 `verify:fast` 给提交前用。
- **输出只报失败**：测试和检查都用精简输出，全绿时只打印一行汇总，避免长日志消耗 token。
- 以后接 GitHub Actions 也只跑这一条命令，本地和 CI 结果一致。
- **不调用真实模型**：真实模型只在 `pnpm eval` 里手动跑（花钱）。

## 5. 内网系统模拟服务（`sim/`）

> 实现：`sim/src/`（E0-3 已有骨架、GitLab、故障注入、控制台；Jira / Tita / Apollo / craft / 环境站点随后续任务加）

### 5.1 模拟什么

一个独立的 Fastify 进程，按模块组织：

| 模块 | 模拟范围 | 依据 |
|---|---|---|
| GitLab | REST v4 中用到的部分：项目、分支、提交、MR（建、查、合并、冲突）、Webhook、个人令牌鉴权。**git 是真的**：裸仓 + `git http-backend`，clone、push、diff 都是真实操作 | GitLab 官方 API 文档 |
| Jira | REST v2：JQL 搜索（只支持我们用到的语法）、状态流转、变更历史、附件、经办人 | Jira 官方 API 文档；状态和优先级取值做成配置（`06` §15 第 3 项未实测） |
| Tita 工单 | 工单查询、节点、负责人、附件 | **假设**：接口说明未拿到（`06` §15 第 2 项），每个字段标「假设」 |
| Apollo | 读配置、发布、回读、回滚到指定版本、本人账号鉴权 | Apollo 开放平台文档；登录方式待实测（`06` §15 第 4 项） |
| `craft` / `tita` CLI | 假 `craft` 命令：`build`（只产出产物与 sha256 清单）、`publish`、`release`、`verify`、`rollback` | `06` §7.1 指令槽 |
| 环境站点 | 按模拟 Apollo 当前生效的版本，在 `http://localhost:4200/env/<环境>/<应用>/` 提供已发布的 demo 站点 | 让「发测试 → 复测 → 核对生效」打到真实发布出去的产物 |

### 5.2 四条原则

1. **连接器不知道自己连的是模拟服务**：只有 baseUrl 和凭据不同。回公司后换成真实地址，连接器代码不改。
2. **可以注入故障**：控制接口 `/__sim/faults` 能制造 429（带 `Retry-After`）、401、超时、合并冲突、发布做到一半中断、Apollo 回读不一致。退避、熔断、断点重试、对账都靠它测。
3. **每个接口标依据**：代码注释写「依据：官方文档 <链接>」或「假设」。回公司后先对真实系统跑一遍连接器契约测试，有差异就改模拟服务。
4. **模拟服务不依赖任何产品代码**（§2.3），自己定义报文结构。

### 5.3 模拟控制台

`http://localhost:4200/` 一个简单网页，给质检用：手动建 Jira / Tita 单、改单状态、开关故障、查看模拟 Apollo 的版本和环境站点、看 MR 列表。风格从简（这是开发工具，不是产品界面，不受设计规则约束）。

```yaml
inject: B003.inject.patch    # 植入 Bug 的补丁，seed 时作为单独一个提交打进主分支
inject_message: 列表排序改用字符串比较   # 植入提交的提交信息，要像正常开发提交，不透露是 Bug
fix: B003.fix.patch          # 参考修复，只用来证明这道题成立
verify:
  unit: B003.test.ts         # 隐藏测试，不进 demo 仓，Bot 看不到
  browser: B003.check.json   # 可选：浏览器断言
expect_files: [src/pages/approvals/sort.ts]
```

改两个仓的题：`repo` 写成列表，`inject` / `fix` 按仓分别给补丁，`verify.run_in` 指定隐藏测试在哪个仓里跑，`expect_files` 带仓名前缀（如 `demo-lib/src/status/status.ts`）。字段由 `tools/fixtures/lib.ts` 校验。隐藏测试运行时放在被测仓的 `src/__hidden__/` 下，按这个位置写相对路径。

- **隐藏测试和参考修复只放在 `fixtures/bugs/`**，不推进模拟 GitLab，防止 Bot 读到答案。
- 每道题入库前自检（`pnpm fixtures:check`）：按主分支的样子打上全部植入后，两仓公开测试和类型检查仍然通过；每道题隐藏测试因断言失败、打上参考修复后通过。要装依赖，不进 `verify`，加题或改 demo 仓时手动跑。
- 题目覆盖 L0～L2：L0 一两行的逻辑错，L1 跨几个文件，L2 碰到高危路径（如权限判断）或改两个仓。
- 规模：E0-4 先做 5 道，S3 前扩到 15～20 道。

### 6.3 一套题库，三种用途

1. `06` §15 第 13 项的基线成功率评测（`pnpm eval`，真实模型）；
2. 端到端冒烟测试（假引擎按参考修复「修」，验证平台链路，每次 `verify` 都跑）；
3. 质检素材：用户验收时直接拿题目提单。

## 7. 测试、完成标准与防跑偏

### 7.1 测试分层

| 层 | 怎么做 | 放哪 | 何时跑 |
|---|---|---|---|
| 单元 | Vitest，只给有分支的纯逻辑写（§7.2） | 与源码同目录 `*.test.ts` | verify |
| 数据库集成 | Vitest + 真实 PG，每个测试文件从模板库克隆一个临时库 | `*.int.test.ts` | verify |
| 越权 | 从系统表列出全部租户表，自动生成「A 空间读写 B 的数据必须失败」用例（`06` §13.5） | `apps/server/test/tenancy/` | verify |
| 推进函数 | fast-check 属性测试 + 每步提交前后故障注入（`06` §3.6） | `apps/server` | verify |
| 推送差分 | 每个测试用户收到的变更 = RLS 下查到的行（`06` §13.5） | `apps/server` | verify（P2 起） |
| 连接器 | 对模拟服务跑，含故障注入 | 各 `plugins/connector-*` | verify |
| 引擎契约 | 脚本化假引擎跑 `AgentRuntimePlugin` 契约（`06` §11.4） | `packages/core-protocol` | verify |
| 端到端冒烟 | Playwright + 假引擎 + 1 道题走完整链路 | `e2e/` | verify（P4 起） |
| 界面对照 | Playwright 截实际页面，和 `reference/images/` 定稿图并排 | 产物放 `~/.cloudcraft-dev/qa/` | 交付界面任务时 |
| 真实模型评测 | 题库 + OpenAI | `tools/eval` | 手动 `pnpm eval` |

### 7.2 测试取舍（省时间、省 token）

测试按价值写，不按函数写；开发过程中不反复跑全量。

**必须有测试的**（出错代价高、人工难发现）：
- 推进函数 `advance()`、状态机、任务租约；
- 多租户隔离与权限（越权测试是自动生成的，加表不用手写用例）；
- 去重、找人、外部副作用的幂等与断点重试；
- 发布与合并（假 `craft` 和模拟服务的故障注入）。

**不单独写测试的**：界面、简单的增删改查、配置读写、胶水代码。这些靠端到端冒烟（一条链路覆盖一大片）、界面对照截图和人工验收。

**聚合着写、聚合着跑**：
- 一个任务结束时，按功能写一组场景测试（一个测试走完一段流程），不给每个小函数各写一个；
- 开发中只跑和改动相关的测试（`pnpm test --filter <包>` 或 Vitest 的 related 模式），**改一点就跑一次全量是浪费**；
- 全量 `pnpm verify` 只在提交前跑一次（推送前钩子会自动跑）。

### 7.3 完成标准

一个任务同时满足以下各项才算完成，可以交验收：

1. `pnpm verify` 全绿；
2. §7.2「必须有测试的」部分有测试；界面任务有界面对照截图；
3. 和 `06` 不一致的地方已在同一提交里改了 `06`；
4. §9 台账状态与交接栏已更新；
5. 写好验收单（§8.3）。

### 7.4 防跑偏：规则尽量交给机器检查

文字规则会随上下文变长被遗忘，**能机器检查的一律做成检查**，过不了 `verify` 就交不了；机器查不了的写进 `.claude/rules/code.md` 的自查清单。优先用现成的 ESLint 插件，自定义规则只写必要的几条（`tools/eslint-rules/index.js`，聚合测试 `tools/eslint-rules/guardrails.test.ts`）。

| # | 防什么 | 怎么查 | 落地 |
|---|---|---|---|
| 1 | 核心代码引用插件、包之间乱依赖 | 自定义规则 `cc/boundaries`（§2.3） | E0-1 ✓ |
| 2 | 按插件名分支（`if (engine === 'pi')`） | 自定义规则 `cc/no-plugin-id-branch`：禁止拿插件 ID 字符串比较 | E0-1 ✓ |

| 4 | 界面文案写死中文 | 自定义规则 `cc/no-hardcoded-cjk`：产品代码的字符串和 JSX 文本出现中文即报错（测试、`tools/`、`sim/`、`fixtures/` 除外） | E0-1 ✓ |
| 5 | 绕过多租户隔离 | 运行账号无绕过 RLS 的权限；自动检查每张租户表都有 RLS 策略和必需列；直接写 SQL 只允许在 repo 层 | P1（要有数据库） |

| 9 | 跳过测试 | 自定义规则 `cc/test-focus-skip`：禁止提交 `.only`；`.skip` 必须注明台账编号 | E0-1 ✓ |
| 10 | 提交密钥 | 提交前用 secretlint 扫描暂存文件（含 OpenAI、GitHub 等令牌格式） | E0-1 ✓ |

- 直接编辑生成物（`index.html`、`reference/src/**`、`openapi.json`、`pnpm-lock.yaml`）和 `.env` 时拦下，提示用哪个命令生成；
- 改完一个代码文件自动对它跑 ESLint，**没问题时不输出任何内容**，有错才把错误反馈回来。

## 8. 协作流程

### 8.1 任务状态

`待做 → 开发中 → 待验收 → 通过`；验收不通过为 `打回`，修完回到 `待验收`。

### 8.2 一次对话的标准流程

1. 读 §9 交接栏，确认当前任务；
2. 大任务开工时先拆成子任务（编号如 `P1-a`），写回 §9，每个子任务对应一次能单独验证的提交；
3. 只读该任务「需读」的章节；
4. 开发 → 测试 → `pnpm verify`；
5. 更新 `06`（如需）和 §9，提交；
6. 交验收单；
7. 结束前更新交接栏。

### 8.3 验收单（写在 PR 描述里，本地阶段写在交付回复里）

```text
任务：E0-3 模拟服务骨架 + 模拟 GitLab
改了什么：……（3～5 条）
怎么验：
  1. pnpm dev:up && pnpm dev
  2. git clone http://localhost:4200/git/demo/demo-web.git → 能克隆
  3. 打开 http://localhost:4200/ → 「故障」里开 429 → 再调接口应返回 429
应该看到：……（附截图路径）
没做 / 已知问题：……
```

### 8.4 Git 规范

- 分支：从最新 `origin/main` 建，`feat/<任务号>-<英文简述>`（如 `feat/E0-1-repo-skeleton`），文档用 `docs/...`。
- 提交信息：中文，`类型(范围): 改了什么`，正文写为什么改、影响什么；类型用 `feat / fix / docs / test / refactor / chore`；不写评价性的话；**一个提交只做一件事，每个提交都能通过 verify**。
- 合并：Claude 在任务分支上提交，推送并开 PR，验收单写在 PR 描述里；**由用户验收后合并**，Claude 不合并。
- 不提交密钥、`.env`、`.claude/settings.local.json`。

### 8.5 文档回写规则

- `06` 某节实现后，在该节标题下加一行 `> 实现：<路径>`，不复述内容。
- 实现和 `06` 不一致：同一提交里改 `06`；属于方向变化的（换技术、改边界）同时写进 `02`。
- 改了 `docs/` 就运行 `python3 scripts/build-index.py`（verify 会检查）。
- `06` §15 的实测结论写回对应章节，并删掉 §15 对应行（`06` §15 原规则）。
