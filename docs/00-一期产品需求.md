# AI Bug 修复工作台 · 一期产品需求

版本 0.11 · 2026-11-20 · 供产品评审

## 1. 一期要解决什么问题

测试在 Jira 报 Bug，线上问题主要经 Tita 工单管理流入。工单交给 AI 后，即使负责人关掉电脑，Bot 也应在公司内网服务器上持续工作，完成定位、修复与浏览器验证。负责人收到通知，可以直接用手机看证据、提意见、打回或通过。

沿用既有「AI 修复」流转思路，重新设计工作台。执行环境按服务器已能访问公司环境处理。以下约定用户能做什么、如何判断完成；接口、客户端框架、部署和网络验证留到技术设计。

### 1.1 产品参照与一期范围

产品参照为 [xAI 的 Grok Bot 官方介绍](https://x.ai/bot)，查阅于 2026-11-20。官网演示了给 Bot 分配职责、让它在自己的计算机上持续工作、在会话里交办和补充任务、教它重复使用的工作方法，以及在需要人决定时带着结果回来。这些交互在本产品里有如下具体含义，开发和验收以本表及第 7 节为准。

| 参照体验 | 本产品一期行为 | 人能看到什么 |
| --- | --- | --- |
| 给 Bot 一份长期职责，让它主动接活 | Bot 按配置定期收取已交给 AI 的 Jira 或 Tita 工单。符合条件的一次交付产生一个任务，负责人关闭客户端后任务继续 | 收单通知、来源、负责人、执行 Bot 和当前进度 |
| Bot 拥有可操作工具的工作环境 | Bot 在指定内网服务器上读工单、改代码，按本轮 Skill 使用服务器浏览器操作目标页面 | 与同一轮次关联的代码差异或 MR、实际操作、证据和未验证项；工作台可直接查看审核所需材料 |
| 在同一段对话里持续协作 | 每张单保留自己的协作记录。负责人可从任一端补充资料；需要协助时 Bot 在原单任务里提具体问题。回答或打回后沿用已有上下文 | 能区分负责人补充、Bot 回复、本轮是否采纳，以及还有什么需要人处理 |
| 教给 Bot 可复用的工作方法 | 使用者创建、导入、选择编码与验证 Skills，平台可提供内置示例。只有人明确保存的经验才成为可复用规则 | 项目能查看启用规则，审核人能回看某一轮实际采用的规则和操作；详见第 4 节 |
| 交回完成的工作，请人决定 | 每轮交付附根因、改动、验证证据和剩余问题。修复人收到桌面或手机通知，可通过或带理由打回 | 重修后能看到针对上轮反馈的变化；通过后保留回原平台人工确认的待办 |

一期聚焦 Bug 修复，内置面向工作台业务的 AI 对话入口（见 1.3）。与工作无关的通用聊天、会议助手、多 Bot 互相转派、观看演示后自动学会新 Skill 等官网能力留给后续独立评估。产品原型中的截图、角色和示例步骤只用于评审呈现，不能据此写死业务规则。

### 1.2 账号、开通与工单归属

**已确认**：PC 和手机都能处理工单，真人修复人负责审核；Tita 取「AI干活」节点负责人。Jira 收单信号已确认，真人修复人字段仍待确认。Bot 是执行者，审核和打回要记录实际操作的成员。

**维护者建议，待产品负责人确认**：一期采用公司身份登录、管理员开通试点成员。采用这个方案时，用户路径如下。身份入口与首批开通范围列在第 8 节，不能假定公司身份服务已经接入。

| 用户遇到的情况 | 建议的产品行为 |
| --- | --- |
| 首次使用 | 管理员开通成员及其项目范围。成员选择「使用公司账号登录」，首次成功后建立工作台身份，无需另设密码或单独注册。未开通者看见开通说明和管理员联系入口。 |
| 接收自己的工单 | 工作台成员可以关联 Jira 与 Tita 的来源身份。收单时先确定原平台的真人修复人，再匹配工作台成员。同名、缺失或多个候选时保留工单，提示管理员处理；匹配明确后向正确成员补发通知。 |
| 日常权限 | 成员查看获授权项目内的工单、证据和附件。通过、打回及标记原平台已确认由该单的真人修复人操作。管理员负责成员、身份映射和项目授权；管理员代审未列入一期。 |
| 手机从通知进入 | 已登录且有权查看时直达工单。登录过期则先登录，再返回原工单；若换了账号或权限已撤销，告知当前账号无权查看，不展示工单内容。 |
| 双端同时审核 | 同一成员在手机通过后，PC 的待办同步消失。若 PC 上仍留着旧页面，提交旧操作时显示已有审核结果，不重复打回或通知。 |
| 停用或负责人变化 | 停用成员后停止其双端访问和新通知，已作出的审核保留署名。仍待其审核的工单列入负责人待处理清单，明确新负责人后再投递。 |

### 1.3 通过 AI 对话操作整个工作台

PC 和手机均提供全局对话入口。在首页可以跨工单提问或办事；从工单、项目或设置页进入时，对话显示当前关联的对象，并允许切换。用户在手机接续电脑上的对话时，可以看到此前选中的工单、已执行的动作和最新业务状态。对话助手代表当前用户使用软件，服务器修复 Bot 负责执行工单任务。两者通过工单及修复轮次关联。

**模块设计约定**：一期每个业务模块都要同时写清「人能看什么、能做什么」「如何用自然语言完成同一件事」「到哪里核对结果」。需要本人完成的登录、系统授权、原平台人工确认等动作，由对话引导到对应入口。后续新增功能也按此约定验收。

| 使用者说的话 | 助手应读取的数据和执行结果 |
| --- | --- |
| “我有哪几张待审核？先看没做浏览器验证的。” | 按当前成员、任务状态和最新一轮的验证记录筛选，列出来源、编号、原因和详情入口。能区分「未执行」「执行受阻」「已通过」「结果未知」。 |
| “这张为什么又退回来了？上轮已经修了什么？” | 将历轮打回意见、改动、实际验证及 MR 对应到同一工单，引用具体记录。找不到证据时说明缺哪项。 |
| “用普通员工再测一次，重点看切换第二个分组。” | 在当前单记录补充及发起人。处于需要协助时按状态继续；处于待审核时根据用户意图发起复测或打回。回复中区分「已提交给 Bot」「正在执行」「已有验证结果」。 |
| “把这个验证 Skill 用到审批项目，下一轮启用。” | 在用户有项目设置权限时，确定项目、Skill、作用范围和生效时机，保存后给出设置入口。其他项目及历史轮次保持原有规则。 |
| “这张我审核通过。告诉我下一步做什么。” | 核对当前轮次和真人修复人资格，记录该成员作出的审核决定，更新双端待办，给出来源原单入口。一期在用户手动完成原平台操作后，才可按其明确指令登记本地确认情况。 |
| “今天 Tita 有正常收单吗？” | 返回最近一次成功采集时间、异常和任务数量；采集失败不能回答成「今天没有 Bug」。成员管理、来源设置等管理操作同样受当前用户权限约束。 |
| “把这轮修复发到测试环境，通知这张单的测试人。” | 明确项目、版本、环境和接收人后，按当前成员的环境发布权限发起任务，返回发布进度；测试环境已生效后发送可测通知。只说「发布」且环境不明确时，先询问目标环境。 |
| “组件已经发了，为什么主站里还看不到修复？” | 定位工单、环境及本次大包，逐项核对已发布的组件版本、子项目实际打入的版本、环境中生效的应用版本和主站接入方式，指出第一个未完成或未核实的环节，附对应记录。 |

**数据要能被 AI 按业务含义使用。** 每个项目、成员、Bot、Skill、来源工单、内部任务和修复轮次都有稳定标识。工单详情、协作消息、变更、验证证据、审核决定和执行记录能按这些标识相互定位。每条关键记录带有来源、产生时间、操作者、状态和结果。截图、录屏和附件关联具体工单或轮次，注明其用途（原单材料、修前复现或修后复测）及是否实际查阅。AI 能按项目、人员、来源、时间、状态和轮次检索、比较或汇总，并给出可打开的原始依据。只在界面上画一个状态、或只在聊天里说“已通过”，无法满足此要求。

**操作与权限**：对话和界面采用相同的可见范围、操作权限及流转条件。建议一期按以下规则处理：查询直接回答；对象明确且具备权限的单项操作直接办理；有多个同名对象或意图不明确时先澄清；批量审核、修改项目通用规则或调整成员权限时先列出对象和影响范围供用户确认。执行后显示已成功、失败或待执行的具体结果，可追溯到发起人和对象。客户端断线、重复发送或其他人先改变状态时，应先核对当前结果，避免重复派工、重复审核。工单和附件中的文字是供分析的材料，不能代替当前用户授权操作。

### 1.4 候选场景：用 AI 读懂失败记录（待试点验证）

**已确定的数据需求**：每次执行失败时，保留所属工单、轮次、失败时间、失败阶段、当时执行的操作、实际错误，以及可供有权限的人和 AI 查看的一手证据（例如对应日志片段、浏览器截图或执行返回结果）。保留后续重试的结果，避免覆盖前一次失败。证据缺失时明确记录缺失项。

**用来检验设计的例子**：负责人问「本周哪些 Bug 修复失败过？现在还有哪些卡着？」助手应说明统计范围，按工单去重，分别列出发生过失败的工单数、失败执行次数、其中重试后已恢复及仍待处理的工单。同一张工单两次失败后第三次修好，计为一张曾失败的工单、两次失败，当前已恢复。

点进某张单追问「为什么没修好」，先给出失败发生在哪一步、证据能确认什么、下一步可以检查什么，再提供关键日志原文的位置供核对。例如浏览器记录显示账号无权进入页面，只能确认复测受阻；现有证据不足以判断代码改动是否生效。

**验证办法**：试点时让修复人用真实失败记录回答「哪些还要我管」「这张卡在哪」「下一步做什么」，把助手回答与原始记录核对，观察能否减少翻日志的时间。这是候选用法，是否需要独立的失败统计页、固定分类或定期报告，待试点反馈后决定。

## 2. 工单如何交给 AI

| 来源 | 收单条件 | 审核人 | 收单时保留的信息 |
| --- | --- | --- | --- |
| Jira | 沿用旧项目 v14 的收单信号：Jira 工作流状态为「AI修复」，按优先级收取 | 原单的真人修复人；旧版批量收单脚本未返回此字段，映射待确认 | 工单编号与链接、标题、项目、优先级、复现步骤、实际及期望结果、版本、评论和附件（以原单提供为准） |
| Tita 工单管理 | 定期收取当前已进入「AI干活」且节点进行中的工单 | 「AI干活」节点负责人，即真人修复人 | 工单编号与链接、标题、产品线、所属模块、反馈来源、节点与负责人、问题说明、沟通和附件（以原单提供为准） |

采集平台和反馈来源分别展示。例如，Tita 工单也可能标记为「产研自测」。同一来源、同一工单的同一次交付只建一项任务，只发一次接单通知。打回后沿用原任务并保留历轮记录。

工作台分别展示两个来源最近一次成功采集时间。采集失败应可见，恢复后补收漏单。收单后若无法确定审核人或目标项目，列入需要处理的异常，说明缺少哪项信息。

## 3. 内部流转与原单确认

| 工作台状态 | 进入条件 | 后续动作 |
| --- | --- | --- |
| 待修复 | 已收单，等待 Bot 开工 | 通知修复人；可提前补资料 |
| AI 修复中 | Bot 开始处理 | 展示当前进展，例如复现、定位、改代码或验证 |
| 需要协助 | 缺关键资料、复现条件或验证受阻 | 说明具体问题，负责人补充后继续；必要时人工接手 |
| 待我审核 | 本轮已交付修复结果，已列明验证结果和遗留问题 | 通知修复人；支持查看证据、通过或填写原因打回 |
| 打回重修 | 审核人指出问题 | Bot 读取反馈开始下一轮；重新提交时展示相对上轮的变化 |
| 审核通过 | 真人修复人接受本轮结果 | 可选择「发布到测试环境」交给测试人复测，同时保留独立的「待原平台确认」待办 |

「原平台确认情况」单独记录。用户在 Jira 或 Tita 完成人工操作后，可在工作台标记「我已在原单确认」。打开链接不算确认，同一张单继续被采集也不会因此再开一轮。Tita 点击「已完成」表示完成当前流程节点；是否还需复测或关闭整单，遵循原流程。审核通过也不代表已上线。

一期所有 AI 修复和审核状态在本系统流转。后续按平台接口支持情况逐步提供状态回写。

### 3.1 在 PC 和手机 App 内审核代码（一期必备）

修复人从「待我审核」通知进入工单，打开「代码变更」，直接审阅 Bot 本轮实际提交的代码。每轮列出关联仓库、基线提交、修复提交、变更文件和 MR 入口。一次修复涉及多个仓库时，能够逐仓查看。授权用户在外网远程接入工作台后，可在 App 内完成代码审核。

- **看改了什么**：按文件查看新增、修改、删除和重命名；逐行标明增删、行号和上下文。可以从任一改动跳到该提交中修复后的完整文件；已删除文件可查看删除前的版本。
- **PC 怎么审**：左侧选择文件，右侧并排或逐行比较，可展开上下文、定位到具体一行。手机默认单列显示差异，支持切换文件、展开代码、查看完整文件，再回到原来的审核位置。
- **怎么问和打回**：选中代码行即可询问 AI「为什么改这里」，回答引用本轮文件和行号。修复人可将代码位置和意见一起提交给 Bot。重修后可切换「相对基线的全部改动」和「相对上轮的改动」，核对反馈是否解决。
- **审核哪个版本**：通过或打回时记录实际审阅的提交及轮次。若手机审阅期间出现新的修复提交，提示查看新增改动后再确认。代码未加载完整或无读取权限时，明确展示缺失范围和原因，不能把缺失的差异显示为零改动。审核通过记录真人审核结论；发布到目标环境由单独的发布动作触发（见 5.1）。

## 4. AI 设置与任务协作

### 编码和验证规则由使用者注入

工作台以 Skill 为单位管理可复用的工作规则。平台可以内置一些编码、验证 Skills 供选用；使用者也可以创建或导入自己的 Skill，在 AI 设置中查看内容、选择启用范围、替换或停用。一个项目可以分别选择编码 Skill 和验证 Skill，同一份 Skill 可以复用于多张工单。

**在线编写（一期必备）。** PC 和手机的「AI 设置 → Skills」并列提供「在线新建」和「导入」。使用者可以从空白开始填写名称、用途和规则正文，也可以打开已有的自定义 Skill 继续编辑；导入的 Skill 使用同一个编辑器。内置 Skill 可复制为自己的版本再修改。

编辑中可保存草稿，稍后从另一端继续。使用者也可以请内置 AI 根据描述起草或修改规则，先检查草稿再决定是否采用。只有具备对应权限的人选择项目并确认启用后，新版本才从该项目下一轮任务开始生效。进行中的任务沿用启动时的版本，历史轮次可回看当时的规则正文。

例如，团队可以为审批项目注入编码规则「优先复用现有表单组件」，以及验证规则「按工单复现路径回归，并记录最后一次交互的结果」。Bot 根据本单材料将规则落实为具体操作。工单没有给出角色或分组名称时，Bot 应标出缺失条件；只有使用者明确保存，单次补充才成为可复用规则。

在「AI 设置」中，使用者看到的是可选和已启用的 Skills、来源（平台内置或使用者注入）及内容。在工单详情中，审核人看到的是本轮实际采用的 Skills、具体执行步骤和证据。规则发生变更后，仍可查看历史轮次当时采用的内容。

| 范围 | 用户可以维护的内容 |
| --- | --- |
| 全局 | 默认 AI 工具或模型、共用修复提示词、允许自动执行的动作、需要人工协助的条件 |
| 项目 | 产品线、模块与仓库的对应关系，环境、业务资料与可用测试角色；为项目选择适用的编码和验证 Skills，并可用自己的规则替换内置规则 |
| 来源 | Jira 测试单重点采集测试版本、复现和预期；Tita 工单保留反馈来源、发生环境、受影响版本及沟通记录 |
| 单张工单 | 修复人通过 PC 或手机补充文字、截图、录屏、操作入口或业务判断；补充和打回原因随本单保留 |

每一轮都能查看 Bot 实际采用的工单材料、规则和最新补充。无法判断版本或账号角色时，Bot 就这个问题请求协助。运行中收到新信息，应让修复人知道本轮是否已采纳。只有用户明确保存为项目规则的经验，才应用到其他工单。

## 5. 服务器执行与浏览器验证

所有 Bot 在指定公司内网服务器上全天候执行。PC、手机退出或断网不会中断修复。单张任务记录目标仓库与版本、当前阶段、交付改动或 MR、验证证据和阻塞原因。交付步骤失败时，重试应复用已完成的工作，避免重复创建修复任务或 MR。

服务器提供浏览器操作、截图和录屏能力。本轮如何复现、如何复测、采用何种证据，按使用者启用的验证 Skill 执行。平台可提供「页面交互回归」作为内置示例，要求在目标环境尝试复现，并在包含改动的版本上复测。审核页区分计划步骤、实际执行、验证结果与待确认项，注明所用环境和版本。

例如「审批中心，发起审批，点击分组界面卡住」：若启用了上述验证 Skill，Bot 可结合原单给出本轮操作，检查点击分组后能否继续交互。具体账号、分组和预期取自所选规则、工单或使用者补充。修复人可以直接在手机上看结果。

### 5.1 一键打包发布与人工提测

**一期已确认**：支持从工单在 PC 或手机发起一键发布，目标分为「测试环境」和「正式环境」。选定版本及目标后，服务器按项目发布配置完成打包、部署并检查目标环境实际生效的版本。客户端可随时关闭，再次打开能接续查看进度。

| 步骤 | 使用者操作与可见结果 |
| --- | --- |
| 发测试环境 | 在工单「发布」页看到修复轮次、提交、涉及应用、目标环境的当前版本及本次将包含的变更。选择或沿用工单测试人，点击「发布到测试环境」。如果实际发布包还包含其他工单的变更，一并列出。 |
| 通知测试人 | 新版本在测试环境生效后，通知指定测试人。通知可直接打开测试入口，并带上工单、已部署版本、改动摘要及待复测步骤。若同一环境后来被新发布覆盖，旧通知提示当前版本已变化。 |
| 记录测试结果 | 测试人针对实际测试的版本选择「通过」或「打回」，可附文字、截图或录屏。打回意见随原单回到修复人和 Bot；产生新提交后，上一版本的测试结果保留在历史记录中。 |
| 发正式环境 | 提供独立的「发布到正式环境」动作，明确列出发布范围、目标版本和对应测试记录。建议默认由有正式发布权限的人发起，发布已通过人工测试的代码版本。正式环境如需按环境配置重新打包，应能追溯到相同源码及发布范围。 |
| 查看结果或重试 | 每次发布记录发起人、工单、应用、提交与产物版本、目标环境、时间、阶段、结果及日志。分别展示打包、部署和生效检查；某一步失败时显示失败位置、已生效范围和重试入口。跨端重复点击可回到同一发布任务。 |

发布状态、人工测试结果、代码审核结论和原平台确认分别记录。工作台按项目配置两个环境的发布目标、入口与角色。测试人、修复人和正式发布人可以是不同成员；PC、手机和 AI 对话使用相同权限。助手能回答「这个 Bug 现在测试环境和正式环境各是什么版本」，并引用两条环境发布记录。正式发布的权限归属、是否强制人工测试通过，以及生产回退策略，留待项目评审。

### 5.2 跨项目大包发布与流转明细（一期）

一次修复可能横跨组件包、子项目和主站。「大包」指为交付同一项修复而一起推进的一组版本与发布步骤。它可以包含多个独立产物。修复人在工单里进入「大包明细」，能看到本轮涉及哪些仓库、为什么涉及、各自要发什么，以及最终从哪个业务入口验收。

**生成发布清单。** 项目维护者配置组件包的使用方、子项目的构建发布方式，以及主站如何加载该子项目。系统结合本轮代码改动和依赖关系给出建议清单，区分「改了业务代码」「需要升级依赖并发布」「只需从业务入口验证」。发布人可核对、增减范围并记录原因。其他项目即使引用同一个组件包，也只在本次修复要求它们采用新版本时进入清单。缺少依赖关系时标明待确认。

**示例：组件 C 的问题影响子项目 A。** 下表使用示例版本，具体项目名称和接入方式由项目维护者配置。

| 步骤 | 依赖与操作 | 该步完成的依据 |
| --- | --- | --- |
| 1. 发布组件 C | 对已审核的组件修复提交打包，发布约定的新版本，例如 1.4.3 | 记录组件提交、包名和确切版本，可供 A 获取 |
| 2. A 升级组件 | 将 A 使用的 C 从 1.4.2 更新为 1.4.3，记录依赖变更；需要锁文件的项目同步更新锁文件 | 可审阅 A 的依赖差异；构建实际解析到 C 1.4.3 |
| 3. 构建并发布 A | 使用确认过的 A 提交构建；将产物部署到本次选定的环境 | 记录 A 的提交、产物版本及其中使用的 C 版本，核对目标环境实际生效的 A 版本 |
| 4. 主站接入并验收 | 若主站固定引用 A 的版本，先更新引用并发布主站；若主站直接加载独立部署的 A，则从实际业务入口验证 | 记录主站是否需要发布、入口实际加载的 A 版本、浏览器验证结果及证据。任一步缺少证据均标明未核实 |

**一键执行与明细。** PC、手机和 AI 对话使用同一份清单。发布人可在开始前看到目标环境、各项当前版本与目标版本、先后关系、关联提交/MR；每步运行后补充实际版本、状态、时间、执行结果和日志。组件 C 被 A、B 两个本次必发子项目引用时，C 发布一次，A、B 可分别升级并发布；依赖两者的主站步骤在两者就绪后执行。

**部分成功、重试与提测。** 如 C 已发布、A 构建失败，大包显示「部分完成 · A 构建失败」，主站依赖步骤显示「等待 A」。重试先核对成功步骤的产物，再从失败处继续；若必须修改组件源码，应发布新的组件版本并将依赖旧版本的下游步骤重新标为待更新。多项目只完成一部分时，详情持续展示各项目当前实际生效版本。目标环境的必发步骤完成且业务入口已核实后，再发整包可测通知，通知关联本次大包版本清单。

**测试与正式分别留痕。** 测试结果绑定当时的组件、子项目和主站版本组合。正式发布前展示与已测清单的差异，区分环境配置或包标识变化与源码、依赖变化；后两者需重新标明受影响的审核和复测范围。正式环境的每步结果单独记录，不能沿用测试环境的「已生效」状态。

### 5.3 报错展示（一期必备）

收单、修复、验证、打包、部署或生效检查失败时，PC 和手机的任务详情直接展示失败步骤及工具实际返回的错误原文。错误码、退出码、文件和行号在工具有返回时一并显示。保留换行，可复制报错并展开对应这一次尝试的上下文日志；凭据等敏感值在展示、复制和 AI 引用前脱敏。若工具超时或没有返回错误文本，明确说明已观测到的情况。

发布失败时，通知相关负责人「哪个环境、哪个项目、哪一步失败」，点击直达本次错误。跨项目大包同时列出已生效、失败和等待中的步骤。AI 解释或建议单独展示，附所依据的日志位置；根因未确认时标注待核实。重试保留上一次的原始错误，方便对照。

### 5.4 Apollo 紧急回滚（一期移动端必备）

**现场依据**：公司 [Apollo 配置中心的 Tita_Static 项目](http://10.128.8.179:8070/config.html?#/appid=Tita_Static) 按环境、集群和 Namespace 管理配置。只读查看时，在 TEST / default / application 看到了发布历史、回滚已发布配置和授权入口；该 Namespace 提示从未发布。正式环境与各子项目、静态资源配置项及历史产物的实际对应关系，实施时核对。

**在家处理线上故障**：值班人从手机首页「紧急回滚」、故障通知或对应发布记录进入，不要求先创建 Bug 或先启动 AI 修复。在授权远程接入下，整次操作在 App 内完成。由公司内网服务按项目授权对接 Apollo，手机不必直连内网管理页面。

1. 选择应用及环境，展示当前生效发布、集群、Namespace、历史记录与可恢复目标。优先呈现有成功验证记录的历史版本，标明依据。若无可回滚历史、旧产物不可用或无法核实作用范围，说明具体原因。
2. 预览当前与目标配置差异、实际会改变的应用和资源版本。按 Apollo 实际支持的粒度列明范围；若一次回退整个 Namespace 会连带恢复其他配置，列出这些变化。涉及跨项目大包时，对照第 5.2 节列出主站、子项目和依赖产物的兼容情况。
3. 具有对应环境回滚权限的真人核对环境、当前版本、目标版本和影响范围后确认。AI 可查询、比较和准备回滚预览；正式回滚需用户明确确认此次操作。若确认时线上版本已变化，刷新差异并重新确认。断网、重复点击或切换设备时可找回同一执行记录。
4. 分别显示请求结果、Apollo 配置回读结果和业务入口验证结果。核对实际加载的资源版本，并按项目回滚验证规则检查关键页面。配置已回退但客户端仍在加载故障版本时，显示「配置已回退，业务恢复待验证」；失败或部分生效时展示原始错误、受影响范围和待处理步骤。
5. 手机推送最终结果，保留操作者、时间、回滚理由、前后版本和验证证据。恢复后可将该记录关联到工单，让 Bot 继续定位根因。配置回滚、代码修复与原平台确认分别留痕。

## 6. 双端工作台与通知

- **PC App**：收件箱、待我审核、需要协助、待原平台确认；查看工单证据、代码改动与执行历史；维护 AI 和项目设置。全局快捷键截图、录屏并附到当前工单是桌面定制候选。
- **移动 App**：从通知直达工单；查看改动、复现与验证录屏；补充文字或素材、通过、打回、跳转原单。系统分享菜单接收截图或录屏是移动定制候选。
- **通知**：接到新单提醒真人修复人；需要协助时说清缺哪项信息；每轮修好后通知审核。PC 提供桌面提醒，手机在 App 未打开时也应收到提醒；错过通知仍可从待办找到任务。两端共用审核结果。
- **公司内外使用**：授权用户在公司网络、家庭 Wi-Fi、移动网络下均可使用同一 App。日常审核的体验目标是无需反复手动登录现有公司 VPN。手机能在工作台内看完审核证据；原平台暂不可达时，保留人工确认待办。Tailscale 是远程访问候选，具体接入方式在实施阶段确定。

## 7. 一期验收场景

**主场景：关掉电脑仍能交付一张可审的工单。** 负责人下班关闭 PC。Tita 工单进入「AI干活」，手机收到一次接单提醒。Bot 按项目启用的 Skills 开始处理；发现缺少复现角色后，在此任务内提问。负责人在手机回复「用普通员工」；Bot 在服务器浏览器按该角色操作，交回改动和实际验证证据。负责人打开通知查看本轮材料，打回并说明另一个分组仍有问题。Bot 保留首轮记录，修订后再次交付。负责人通过，PC 同步结果，工作台保留待回 Tita 确认的事项。各动作都能从同一张单追溯。

| 场景 | 可观察的通过条件 |
| --- | --- |
| 用手机对话完成审核 | 修复人询问「还有哪张没复测」，点开回答引用的证据，要求某张单按补充条件重测。Bot 接到一次任务，PC 能看到同一轮次和发起人；在结果产生前，对话显示待执行或执行中。 |
| 权限与状态一致 | 无权成员通过对话查询其他项目时看不到工单或附件，也不能代他人审核。已通过的任务收到旧会话里的打回指令时，提示最新状态，不静默改写原决定。 |
| 通过对话调整项目规则 | 有权限的用户确认项目与 Skill 后启用规则，设置页能看到同一变更。下一轮展示实际采用的规则，历史轮次可回溯。 |
| Jira 收单 | 把一张测试 Bug 交给 AI，出现一项任务，真人修复人收到通知。连续采集不会重复开工。 |
| Tita 收单 | 工单整体为「解决中」且「AI干活」节点进行中时收单，通知节点负责人。只满足整体状态时不收单。 |
| 人离开电脑 | 电脑关机后 Bot 继续工作；负责人在家用手机补充测试角色，Bot 接续原任务并展示采用的条件。 |
| 使用者注入 Skills | 使用者为项目启用自定义编码 Skill，用自己的验证 Skill 替换内置示例。下一轮按选定规则写代码和验证；审核人能查看两份规则的来源、当轮内容、对应改动与验证结果。 |
| 在线编写 Skill | 在 PC 在线新建验证 Skill 并保存草稿，手机可打开并续写。保存草稿后 Bot 仍沿用当前规则；确认在指定项目启用后，下一轮采用新版本，上一轮仍能查看原版本。 |
| 浏览器复测 | 审核人能辨认改动版本、复测步骤和结果；证据缺失时看到原因，不能把仅构建成功显示成页面验证通过。 |
| 手机审代码 | 负责人在家庭网络从通知进入「代码变更」，在 App 内查看逐行差异和修复提交的完整文件，选中一行打回。PC 同步显示该行与意见。重修后手机能单看相对上轮的改动，审核通过记录对应的新提交。 |
| 一键提测与上线 | 修复人在手机选择本轮提交发测试。测试人从可测通知进入指定环境，记录该版本的复测结果。获正式发布权限的成员选择已测版本上线，工单中可核对两个环境分别生效的版本、发起人和时间。 |
| 跨项目大包与断点续发 | 同一组件供 A、B 使用，两者本次均须发布。组件发包成功、A 成功、B 失败时，手机可看到三个实际结果、B 的失败原因及主站等待项。修复并重试 B 后核对 A、B 使用的组件版本和主站实际加载的版本，才发出整包提测通知；历史清单和各次尝试可追溯。 |
| 发布失败与重复操作 | 模拟打包通过但部署失败，界面显示部署失败及证据，测试人不会收到「可测」通知。重试成功后通知一次；旧客户端重复提交不会再次部署同一任务。 |
| 报错可定位 | 子项目 A 构建返回带文件、行号的错误时，负责人从手机通知直达该次构建，能复制实际报错、展开日志，并看到主站在等待 A。在 PC 或 AI 对话中查看同一次失败时，错误与界面一致。 |
| 在家用手机紧急回滚 | 全程关闭 PC。值班人从手机选择正式环境发布，看到配置差异和受影响应用，确认后退出 App。再次进入可查看同一回滚结果、实际生效版本及业务验证；仅配置成功时不宣告故障已恢复。无权限成员只能看到其权限允许的信息。 |
| 手机打回与再审 | 手机打回后 PC 同步状态；Bot 读取反馈，保留两轮差异，重新通知同一人。通过后仅保留一次待原平台确认。 |
| 平台人工确认 | 用户可跳回来源平台、完成对应操作并回来标记；系统能区分审核通过、已打开链接和用户已确认。 |
| 网络或采集恢复 | 手机从内网切到移动网络后能继续审核同一任务；来源采集短暂失败可见，恢复后漏单可补、已有任务不重复。 |
| 账号开通与回跳（按建议方案评审） | 已开通成员首次登录后可见授权项目；未开通者看到开通说明。同一人手机登录过期时，点通知并重新登录后回到原工单。 |
| 身份和审核权限（按建议方案评审） | 两名同名成员不会因显示名相同收到彼此的审核任务。映射待处理时保留工单；确认归属后通知正确成员。非修复人无权代审，停用成员无法通过旧通知继续访问。 |

## 8. 下轮评审待定

1. Jira 从哪个字段取得真人修复人；Tita 节点多人负责时谁有权作最终审核。
