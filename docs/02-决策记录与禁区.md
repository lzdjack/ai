## 一、风格方向

| 被否掉的 | 用户原话 / 原因 | 正确做法 |
|---|---|---|
| 后台管理风（侧边菜单加表格加卡片墙） | 「不好看，不要做的跟后端管理一样」 | 苹果系毛玻璃，像原生应用 |
| 可点击的产品原型、线框图 | 「我要的不是产品原型图，我要的是 UI 设计图」 | 高保真静态设计图（PNG） |
| 「炫酷」做成霓虹、赛博、粗野主义、杂志风 | 「你现在做的太抽象了」，要好看、功能方便 | 炫酷 = 精致的苹果质感，不是怪风格 |

| 底部大胆的浮动操作区、扇形菜单、岛屿 | 「太夸张了」 | 常规结构：左菜单、三栏面板、对话底部输入框 |

## 四、工作方式（同样重要）

1. **先出一张精细图，确认后再铺开。** 用户原话：「不要多出，出个精细的设计图，我满意了你再做全部」。
2. **只改用户指出的位置。** 用户截图圈出一块，就只改那一块，其余保持不变。
3. **要备选时，做成一张对比图**，并排放 3 到 4 种，标上编号和一句话说明，亮色和暗色都要。不要散着出一堆单独的文件。
4. 每版都出亮色和暗色。
5. 本地 HTML 渲染成 PNG，**不上传网络**。
6. 交付前自己先看一遍渲染结果：文字有没有换行、有没有元素重叠、有没有被遮挡、有没有冒出旧的图标，有就先修好再给用户。
7. 不要自己改用户已经定下的东西。用户没提的部分沿用定稿。
8. **所有给人看的文档和设计统一收口进唯一的 `index.html`**（2026-11-23 用户确认：「以后都放到一个 html 文档里面，这样就一个就行了，不需要再到处乱找了，他是一个集合」）。产品需求、修复流转方案、链路流转、设计主题、PC / 移动端设计图、技术设计方案（`06-技术设计方案.md`）、决策与后续全部通过 `scripts/build-index.py` 汇入根目录唯一的 `index.html`，不再另开分散的 HTML 文档；每次更新文档或设计图后重新运行构建脚本。

- **平台骨架定案（2026-11-27，P1，详见 `06` §2.3、§2.8、§3.6）**：
  - **RLS 由建表助手的清单生成，每次迁移后重放**：表结构走 drizzle-kit 生成的版本化迁移；RLS 策略、`FORCE`、授权、只追加触发器、漏写探针由清单生成一份可重复执行的 `security.sql`，窄函数写在 `functions.sql`（`CREATE OR REPLACE`），都在迁移后重放。这样新表只要用建表助手建，隔离就自动跟上，越权测试再从系统表兜底。
  - **`events` 手写分区迁移**：drizzle-kit 不支持分区表，`events` 用一份手写迁移建（按月分区 + 默认分区），Drizzle 定义只用于类型化读写、不进 drizzle-kit 的 schema。
  - **窄函数要跨空间时只开最小口子**：`FORCE` 会把表主人 `cc_migrator` 也挡住，所以只在窄函数要用的 5 张表上加一条只对 `cc_migrator` 生效的放行策略，不给它 `BYPASSRLS`（改角色属性要超级用户，也比按表放行宽）。
  - **漏写检测挂在所有业务表上**：比原定的 9 类配置表更宽，`events` 多一列 `txid` 用来对账；基础设施表（任务队列、Outbox、副作用、推送流）不挂。
  - **`work_items` 单例键带上 `workspace_id`**：避免不同空间的键互相冲突、也不泄露别的空间有没有这个键。
  - 被否掉的：策略直接写进 Drizzle（`pgPolicy`，drizzle-kit 生成不了 `FORCE`，策略和 `FORCE` 会分在两处）；给 `cc_migrator` 开 `BYPASSRLS`；`events` 不分区（`06` §2.8 要求能整块清理过期数据）。
- **编排底层自己实现，不用 DBOS（2026-11-27，S2 实测后定，详见 `06` §3.6「S2 对比结论」）**：
  - **同样 3 个场景真杀进程对比**：自己实现的一侧全过；DBOS 5.5.0 一侧 11 项检查只有 4 项不加额外代码就符合方案。关键差别：改了工作流代码后旧版本等着的单没人接管（固定版本号则直接报「不确定」失败，只能每次都按 `DBOS.patch()` 写）；发布杀进程后默认自动重放、外部发布 2 次，也做不到「停下等人点重试」；系统表没有 RLS，工作流入参出参跨工作空间可读；远程执行器仍要 `work_items` 租约，会变成两套队列。
  - **执行计划 v1 补齐**：按仓扇出与汇聚（默认全部成功，可配允许部分继续）、失败按 `on_fail` 自动回到指定节点（次数上限）、人工打回到任意节点、执行中断（有外部副作用在途时进程死掉）停下等人。重试一律追加 `attempt_no + 1`，`node_runs` 唯一键加上 `repo_id`。
  - **外部副作用的幂等键不含尝试次数**：同一个变更（含要发布的版本）无论第几次尝试都是同一个键，重试时才能先回读、不重复执行；执行抛错时状态保持「待定」，下次先回读。
  - **过期租约回收用和认领同样的窄函数**：`sys_claim_expired` 给过期的任务换一张新租约（`fence` 加一）后，在该工作空间的事务里决定续跑还是标中断，不给运行账号开跨空间读。
  - 被否掉的：DBOS 作编排底层（理由见上，不再评估）；把执行中断当普通失败走自动回退（外部可能已生效，必须人确认）。
- **执行器骨架定案（2026-11-27，E1，详见 `06` §5.3a、§2.3、§2.12）**：
  - **执行器协议先走 HTTP 轮询**：`heartbeatAndPoll` 本来就是轮询，HTTP POST + JSON、帧上限 64KB 就够；WSS 隧道等远程执行器（M3）再加，接口不变。7 个 RPC 先做注册、心跳领活、写回三个，其余随用到它们的任务（E2 / P3 / P4）。
  - **长期密钥在执行器本机生成**：注册时只上报密钥的哈希和 `bot_exec` 公钥；`runners` 表加 `enroll_token_hash`、`enroll_expires_at`、`auth_token_hash` 三列，`status` 用 `pending / online / revoked`，在线与否按最后心跳现算。
  - **执行器入场是 B 类握手**：`app_enter_runner(runner_id, 密钥)` 核对后进入执行器所属工作空间；领活就在这个事务里认领，不再加跨空间的认领函数。
  - **`runners` 不挂漏写探针**：心跳每几秒写一次，挂探针就要每次心跳都记操作记录；注册、排空、吊销照常经统一写入记录。
  - **执行器崩溃后自己清场**：容器带执行器标签，重启时清掉上次留下的容器和工作目录；租约由服务端回收，回队列保留原排队时间（排在最前）。
  - **E1 的克隆凭据暂放执行器本机配置**（`CC_RUNNER_GIT_TOKEN`），P3 换成凭据信封下发；凭据只走请求头，不进 `.git/config`、不进容器。
  - 被否掉的：服务端生成长期密钥并在注册响应里下发（多一次密钥在网络和日志里出现）；心跳写进 `events`（每台执行器每 5 秒一条，淹没真正的操作记录）。
- **AI 进沙箱定案（2026-11-27，E2 前半，详见 `06` §5.4、§5.7、§11.4、§2.12）**：
  - **E2 拆两段**：先做引擎契约、Pi 插件、宿主工具校验、模型代理进程、AI 节点与回放判定；浏览器产物替换与截图另做一段（E2b），它要先有被测站点和 Playwright 镜像。

  - **一段执行节点留在同一台执行器**：写回时带 `take_next`，同一流程打开的下一个沙箱节点在同一事务里租给自己，工作区（克隆、依赖、未推送的改动）不用在节点之间搬。没有新增表和任务类型。
  - **模型代理单独进程，控制走本机 Unix Socket**：模型密钥只在代理进程里；执行器靠文件权限（0600）登记每轮令牌，不再多一个共享密钥。工具端留在执行器进程里，每轮一个只听本机的服务。
  - **熔断按「同一个调用连续失败」计**：复现测试按要求先失败，测试命令连续失败是正常干活；同一工具同一参数连续失败 3 次才算死循环。
  - **回放通过才推分支**：判定在推送之前，推上去的 `fix/` 分支都是机审过的；仓库的测试、类型检查命令放进执行计划的仓库信息，由 P3 的仓库探测填。
  - **E2 的提单材料暂放在 AI 节点配置里**，P4 有了轮次表后从轮次读；E2 的分支名按流程编号（`fix/<流程号前 8 位>`），P4 换成 `fix/<slug>/<no>`。
  - **删掉 `pnpm pi:try`**：`pnpm runner:fix` 走真实执行器和三节点流程，保留了隔离自检和隐藏测试复核；插话和会话恢复的结论已写进 `06` §5.4，脚本可从提交 `f0f525f` 取回。
  - 被否掉的：插件自己调 `docker run`（每个引擎各写一遍网络与清场）；工具端单独起进程（它要读写工作区、跑 git，本来就属于可信执行器）；回放失败也推分支（推上去的分支会混进没过机审的提交）。

  - **环境站点每个环境单独一个端口**：Vite 等构建默认从根路径引用资源，放在 `/env/<环境>/<应用>/` 下要改构建配置；单独端口也更像真实环境的独立域名。原定的 `4200/env/...` 路径改为测试环境 `4201`。
  - **修前也用替换后的页面判定**：修前、修后都在同一个环境页面上各换一次本地构建，不拿环境里已部署的版本当修前，因为环境的版本不一定等于本轮的基线提交。
  - **Bot 先按源码写复现物，不给交互式浏览器**：真实模型（B001）不开浏览器写出的复现物一次通过；给 AI 的 ARIA 快照工具等到 P5 证据页一起做。
  - 被否掉的：浏览器跑在宿主机上只靠请求拦截做隔离（拦截管不到 WebSocket、DNS 预取等，且 Chromium 直接在宿主机执行 Bot 的代码）；浏览器容器挂在本轮内部网络上走中继（还要再开一条转发，且仍需要白名单）；修前直接截环境里的旧版本（不一定是本轮的基线）。

- **账号与权限定案（2026-11-27，P2，详见 `06` §2.3、§3.7、§10.1）**：
  - **访问令牌用自签名短令牌（15 分钟），刷新令牌入库并轮换**：用过的刷新令牌再出现，就吊销这个账号所有会话（判定为被盗）。访问令牌不入库，撤权靠每个请求的 `app_enter` 实时核对成员身份。
  - **密码用 Node 自带的 Argon2id**（OWASP 最低参数 19 MiB / 2 轮），不引第三方库。
  - **注册不暴露账号是否存在**：已注册的邮箱照样回 202，邮件里说明「已有账号，直接登录」。
  - **「本人」行的 RLS 读写分开**：读要求本人，写只要求同一空间，给别人发通知不用开新的窄函数。
  - **推送的行由每条连接在自己用户的 RLS 下读**：中继只发号和 `NOTIFY`，不替用户决定能看什么，所以推送和查询永远一致。
  - **限流一小时一个窗口**，按 IP、邮箱、账号分别计；上限可配（`CC_AUTH_RATE_LIMIT_PER_HOUR`，推荐 10）。
  - **新依赖**：`@fastify/websocket`（单条 WebSocket）、`nodemailer`（SMTP 发验证码）、`intl-messageformat`（服务端渲染邮件、通知、报错，和客户端用同一份词条）。
  - **登录 / 注册页面随 P3 开工流程一起做**：P2 交付接口、测试和演练，界面和开工向导连成一条流程。
  - 被否掉的：访问令牌入库（每个请求多一次查询，撤权已经由 `app_enter` 保证）；中继按用户算好推送内容再发（两套权限判断，迟早对不上）；给通知开 `SECURITY DEFINER` 写入函数（读写分开的策略就够了）。
- **接入代码仓定案（2026-11-27，P3a，详见 `06` §2.10、§10.3）**：
  - **P3 拆两段**：P3a 是接口、凭据信封、连接器、探测和执行器侧，验收要点「接入 demo 仓、探测出构建命令、试构建通过」靠它就能证明；P3b 是登录 / 注册页面和四步向导，界面任务单独验收。
  - **信封里放连接器算好的 git 认证头**：执行器只管把这一行头带给 git，不知道是 GitLab 还是别的平台，换平台不改执行器。
  - **执行器只能取本步计划引用的凭据**：服务端核对租约和计划里的 `credential_ref`，拿不到别的仓、别的空间的凭据；每次下发记 `secret_deliveries`，被盗时知道要重签哪些。

  - **人工覆盖存值不存键名**：`repo_targets.manual_overrides` 存「字段 → 值」，推测单独存，读时合并；比只存被覆盖的键名多了值本身，否则覆盖值没地方放。
  - **探测先用确定性规则**：按文件推出命令和验证方式，每条带说明；AI 推测（`06` 写的「AI 自动探测」）在规则推不出来时再补，随 P3b 的「体检」一起做。
