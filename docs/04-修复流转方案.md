# 修复流转方案（技术设计输入）

这份文档写**系统实际要怎么跑**，不写界面长什么样（界面见 `01-设计主题.md`）。内容来自两处：

- 设计评审时用户确认的公司实际流程（2026-11-20）；
- 本机 `@tita/cli` 2.5.5 源码（`tita build`、`tita release`），按源码推出的行为都标了「源码」。

做后端、Bot 执行器、发布模块的人以这份为准；和界面图冲突时先问，再两边一起改。

---

## 0. AI 从哪来

- 全公司一套 AI 连接，管理员在「设置 → 全局 AI」接一次（或管理员第一次用时在步骤器第一步接）：AI 工具、模型、公司网关地址或 API Key、访问令牌。令牌加密存在内网服务器，只给 Bot 用。
- 「试一下」= Bot 在服务器上真实调用一次模型；开工步骤器第 8 步「检查并开工」和「设置 → 项目」都会检查 AI 是否连通，没连通挡住开工。
- 全局还管：Bot 可以自己做的事（发正式环境永远锁定为真人）、什么时候停下来找人、共用修复提示词。改动从下一张单开始生效。
- AI 执行引擎默认内置 **Pi 轻量内核（`pi-ai` + `pi-agent-core` + `pi-coding-agent`）+ 多模型支持**（OpenAI 兼容网关 / Anthropic / Gemini / Ollama；公司内部试点可配网关 `gpt-6.2-sol`），Bot 走隔离容器 RPC，对话助手直连 `pi-ai`（2026-11-24 更新确认，详见 `06-技术设计方案.md` 第 11 节）。
- 待确认：连接方式（图里按公司网关画）；模型是否允许按项目单独选。

## 1. 一张单从哪来

| 来源 | 收单条件（每个项目自己配） | 去哪个环境复现 | 测试人 |
|---|---|---|---|
| Jira（测试提的 Bug） | 项目 + 状态「AI修复」 | 按来源统一设置，默认测试环境 | 提单人 |
| Tita 工单（线上问题） | 产品 + 节点「AI干活」进行中 | 按来源统一设置，默认正式环境 | 没有，修复人在发布页当场选 |

- 复现环境**按来源统一设置**，不读工单里的环境字段，也不因为工单没写环境去问人。
- 审核人 = 工单里的修复人（Jira 经办人 / Tita「AI干活」节点负责人）。Tita 节点有多个负责人时，任一负责人都能审，谁先审算谁的，其他人的待办自动消失（2026-11-21 用户确认）。
- 测试数据和要用的账号由工单提供；工单里写的账号必须在项目的「环境与账号」里登记过才会用来登录，对不上就不登录，在单里提醒先登记。

## 2. 仓库和分支

每个项目有若干 GitLab 仓库，每个仓库各自配：

| 配置 | 说明 |
|---|---|
| 主分支 | 修复分支从这里拉，正式环境从这里打包。各仓库不同（如 `master`、`main`） |
| 测试分支 | 发测试环境用。各项目不同（如 OKR 是 `dev-okr`，薪酬是 `dev-salary`）；只用来验证、不改代码的仓库（主站）没有 |
| 构建命令 | Bot 开工前试构建用（见第 4 节），从 package.json 推测，开发者可以改 |

Bot 用管理员开好的 GitLab 账号（如 `bot-fix`）拉代码、建分支、提 MR，不用个人账号。

**一张单的分支流转：**

```
主分支 ──拉出──▶ fix/<工单号>          Bot 在这里改代码、提交
                    │
                    ├─ MR → 测试分支    ★ 要审核，审核通过才合入
                    │      └─ 在测试分支上 tita build → tita release --env TEST → 通知测试人
                    │
                    └─ 测试通过后 MR → 主分支   ★ 要审核
                           └─ 在主分支上重新 tita build → tita release --env PROD（正式发布人确认）
```

- **进测试分支、回主分支都要审核**，两次 MR 都不能由 Bot 自己合。审核人按项目设置来定：开工准备第 2 步（之后在设置 → 项目）分别设「合入测试分支」和「合回主分支」的审核人，前者默认工单的修复人。
- **正式环境一定重新打包**：合回主分支后在主分支上 `tita build`，不复用测试环境的包。
- 测试打回：意见回到修复人和 Bot，在同一个 `fix/` 分支继续提交，再走一次「MR → 测试分支」。

## 3. 打包和发布（`tita` CLI）

两条命令都在**仓库根目录**执行，且 `tita release` 必须在同一目录、`tita build` 之后执行（它读本地 `dist/`）。

### `tita build`（源码）

1. 读 `package.json` 的 `name` 和 `packageManager`，用对应工具（pnpm / npm / yarn，默认 yarn）从内网 registry 装依赖；默认先删 `node_modules`，`--noRm` 不删。
2. 执行 `npm run build-prod`。**不分环境**，测试和正式打的是同一种产物，区别只在后面发到哪个 Apollo 环境。
3. 把 `dist/` 上传到 OSS 的 `ux/<name>/release/dist/`（已存在的同名文件默认跳过）。

### `tita release --app <app> --env <env>`（源码）

- 作用：**更新 Apollo 配置**，让目标环境加载这次打出来的文件。不重新打包、不上传文件。
- `--env`：`DEV` / `TEST` / `LABS` / `PROD`，默认 `TEST`。
- `--app`：`www`（Apollo 应用 `Tita_Static`）/ `okr`（`okr.tita.work`）/ `assess`（`assess.tita.work`），默认 `www`。每个项目在发布配置里选。
- `--integrity`：生成 integrity；`app=www` 时总是生成。
- 需要 `package.json` 里有 `configFile`（Apollo 里对应的配置名）。
- 版本号**不用传**：从 `dist/` 里的文件名读出版本，替换 Apollo 配置里的资源地址；同时把当前 `git rev-parse HEAD` 写进配置的 `<CommitId>`，发布标题是版本号。

### 发测试环境

谁能发：项目里的「发测试的人」，默认工单修复人，可改成指定的人或「任何人」。

直接 `tita release --env TEST`。**不用 `tita test-release`（提测版本）**，用户已确认那条路不对。

### 发正式环境

- **必须测试通过**才能发正式，没通过的版本界面上不给发。
- 正式发布人是项目里的一个选项，**默认「任何人」**（有工作台权限的项目成员都能发），可以改成指定的人。
- 谁能紧急回滚也是项目里的一个选项，默认同正式发布人，可以改成指定的人；测试环境回滚不限（2026-11-21 用户确认）。
- Jira 单的测试人默认是提单人，发测试前可以换；提单人不在工作台或已停用时必须选一个才能发（2026-11-21 用户确认）。
- 正式环境就是 `tita release` 加 `--env PROD`，不需要另外的配置。注意：源码里 `--env` 默认是 `TEST`，所以 Bot 执行正式发布时必须显式带 `--env PROD`。
- 一期只有测试和正式两个发布目标，**不做 `LABS`**。

### 发完怎么确认生效

Bot 读目标环境 Apollo 配置里的 `<CommitId>`，和本次构建的提交号对上，才算生效，才发「可测」通知。对不上（比如被别的发布覆盖）就不通知，在单里说明。

### 紧急回滚

**只回滚 Apollo 配置**（如 `Tita_Static` 的上一个发布），不重新打包、不重新上传。界面见「紧急回滚」页。

## 4. 开工前 Bot 怎么试构建

- 用 `package.json` 推测：看 `packageManager` 决定装依赖的工具，构建脚本优先用 `build-prod`（就是 `tita build` 内部跑的那条），没有再找 `build`。
- 只装依赖 + 跑构建脚本，**不执行 `tita build`**：它会上传 OSS，试构建不该产生线上文件。
- 推测不对时开发者在第 2 步「构建命令」里改。

## 5. 跨仓库依赖（大包）

- 开工前不配置依赖关系。Bot 每次修复时读当时的 `package.json`（例如薪酬用了 `tita-ui-kit 1.4.2`）。
- 主站从哪个地址加载子项目，来自「环境与账号」里填的环境地址。
- 读不出来的，在工单「大包明细」里标「待确认」，由发布人核对。
- 发布顺序：组件包 → 升级使用方依赖并构建发布 → 从主站入口验证。

## 6. 账号

- 按环境登记，数量不限，同一角色可以多个。
- 每个账号有数据权限：只能查看 / 可以修改。Bot 只按权限判断能不能动数据，不区分「测试号 / 真实用户」。
- 凭证是密码或 Cookie；Cookie 账号不用填账号名，Bot 登录后自己识别。加密保存，只给 Bot 用。

## 7. 规则（Skills）

- 新项目默认只用系统内置的规则。
- 项目自己的规则在开工准备里当场写或让 AI 起草，确认后才启用；从下一张单开始生效，进行中的单沿用开始时的版本。

## 已确认（2026-11-20）

- 发测试环境用 `tita release --env TEST`，不走 `tita test-release`。
- 两次 MR 的审核人按项目设置来定。
- 两次 MR 都**单独审核**：合入测试分支的 MR 不沿用工单代码审核的结果，审核人就是修复人也要再点一次；审核通过后由工作台调用 GitLab 合入，不让人再去 GitLab 点。
- 合回主分支的 MR 不自动提：测试复测通过后，由修复人在工作台点「合回主分支」，Bot 才提 MR。
- 发测试的人是项目里的一个选项：默认工单修复人，可改成指定的人，也可以是「任何人」。
- 工单完成由工单负责人点「修复完成」，不按条件自动完成。
- 正式发布人默认「任何人」，可改；正式发布前必须测试通过。
- 一期不做 `LABS`，正式环境就是 `tita release`，不加额外配置。

## 已确认（2026-11-21）

- Apollo 账号由使用者自己在工作台里配，谁点发布 / 确认回滚就用谁的账号。`tita release`（源码）直接连 Apollo 时用的是 CLI 内置凭据、操作人固定 `deployuser`，所以工作台改为：用本人账号读出当前配置 → `tita release --local-config <目录>` 在本地生成新配置 → 用本人账号写回并发布。详见 `06-技术设计方案.md` 7.2。
