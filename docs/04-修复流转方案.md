# 修复流转方案（技术设计输入）

这份文档写**系统实际要怎么跑**，不写界面长什么样（界面见 `01-设计主题.md`）。内容来自两处：

- 设计评审时用户确认的公司实际流程（2026-11-20）；
- 本机 `@tita/cli` 2.5.5 源码（`tita build`、`tita release`），按源码推出的行为都标了「源码」。

做后端、Bot 执行器、发布模块的人以这份为准；和界面图冲突时先问，再两边一起改。

## 0. AI 从哪来

- 全公司一套 AI 连接，默认由具备全局 AI 管理权限的成员在「设置 → 全局 AI」接一次（或管理员首次用时在极简向导第 0 步「连接 AI」接）：AI 工具、模型、网关地址与令牌（令牌加密存服务端，支持按项目级覆写非密钥模型与行动策略）。
- 「试一下」= 实测真实调用一次模型；向导体检和「设置 → 项目」都会检查 AI 是否连通，没连通挡住开工。
- 全局默认配置（均允许在项目/工作流层级按需调整，仅内置推荐安全默认值）：Bot 可自主执行的节点范围（正式环境高危发布默认锁定真人二次确认）、提问停下条件、共用修复提示词；改动从 **下一轮任务（新单首轮或打回重修下一轮）** 开始生效。
- AI 执行引擎默认内置 **Pi 轻量内核（`pi-ai` + `pi-agent-core` + `pi-coding-agent`）+ 多模型支持**（OpenAI 兼容网关 / Anthropic / Gemini / Ollama；公司试点可按配置填内网模型），Bot 走隔离容器（或无容器本机沙箱）执行，对话助手走独立出站代理直连 `pi-ai`（2026-11-24/26 更新确认，详见 `06-技术设计方案.md` 第 11 节）。

## 1. 一张单从哪来

| 来源 | 收单条件（每个项目自己配） | 去哪个环境复现 | 测试人 |
|---|---|---|---|
| Jira（测试提的 Bug） | 项目 + 状态「AI修复」 | 按来源统一设置，默认测试环境 | 提单人 |
| Tita 工单（线上问题） | 产品 + 节点「AI干活」进行中 | 按来源统一设置，默认正式环境 | 没有，修复人在发布页当场选 |
| 手动新建工单（独立使用 / 临时救火） | 列表顶部点 `+` 直接新建（自动编 `M-<序号>`） | 建单时选项目已登记环境 | 发测试时当场选；**不生成原平台确认待办** |

- **复现环境确定规则**：默认按来源统一设置，**仅当项目触发器显式配置了原单环境提取映射（`env_field_mapping`）且匹配到已登记环境时优先采用**；未配置映射或原单未写时不问人、走来源默认环境。
- 审核人 = 工单里的修复人（`ticket_assignees[]`，支持单人或多人）。当项目存在多名候选负责人时，由项目可配协作策略 `assignee_claim_mode` 决定（默认 `'first_reviewer_claims'`：第 4 步先审核通过者在事务中锁定为主导人并清退其他 `auto` 候选待办；被打回重开且无 `manual` 人工锁定时重新放开；亦支持 `'shared_all'` 或 `'countersign'` 会签），**底层不写死任何外部厂商分支**（2026-11-26 去硬编码升级）。
- 测试数据和要用的账号由工单提供；工单里写的账号必须在项目的「环境与账号」里登记过才会用来登录，未匹配或缺失对应角色凭据时立刻转「需要协助（`ask_user` / `AUTH_REQUIRED`）」等待补齐（允许用户显式点「跳过登录纯代码修复」放行）。同环境同角色多个账号按排序健康绿标优先调度并支持过期自动切下一备用号；`read_write` 写账号支持开启并发互斥锁。

## 2. 仓库和分支

> **可定制与试点预设说明（2026-11-26 更新）**：下方分支拓扑、`tita` / Apollo 命令、双环境发布流程均作为**公司试点的默认内置预设**；按工作台「配置优先于写死」原则，所有流程节点、是否使用测试分支、自定义多环境（`env_code / env_tier`）、工具链构建/验证方式（前端 `dist/` 替换 vs 后端单测/接口探测）、节点绑定专属 Skills 均可在「设置 → 项目 → 流程模板」与连接器里按需定制。

每个项目可关联一个或多个物理代码仓及可构建目标（支持 Monorepo 子包），分别配置：

| 配置 | 说明 |
|---|---|
| 主分支 | 修复分支默认从这里拉，高优先级/生产环境从这里构建。各仓库自配（如 `master`、`main`） |
| 测试分支（可选） | 发预发/测试用（如 `dev-okr`）；无测试分支的单主干仓、只读参考仓留空，工作流自动切换单主干直合模式 |
| 构建与工具链 | 按仓库 `ToolchainAdapter` 自动探测（支持 `pnpm/npm/yarn/bun/go/python/java` 与 Monorepo `--filter`），可微调 |

Bot 使用在 **「设置 → 连接器」** 登记的机器代码源账号拉取代码、推送 `fix/`（默认模板 `fix/<project_slug>/<ticket_no>`，按仓库可配），不借用个人 PAT。

**默认双段分支流转 & 冲突兜底规范：**

```text
主分支 ──拉出──▶ fix/<项目>/<工单号>      Bot（或人工接手）在此改码提交
                    │
                    ├─ [可选] CR/MR → 测试分支  （冲突时自动建 port/<单号>-r<轮>-<试>-<测试分支> 真合并 --no-ff，绝不把测试分支反向合入 fix/）
                    │      └─ 在测试分支合入提交上 craft build → craft release → 核对生效 → 通知测试人
                    │
                    └─ 满足前置后 CR/MR → 主分支（主干冲突时外部关 MR → 退回「打回重修」开新轮解决并重过验证）
                           └─ 在主分支最新提交上重新 craft build → craft release（由项目配置的发布人确认）
```

- **可控测试分支基线重置**：当测试分支被废弃功能长期污染需要从主干重切（`B_new`）时，仅当满足目标主干/生产基线条件（`is-ancestor` 校验）才放行重置，重置同步清理旧 open MR 与 `port/*` 分支。
- **独立 MR 审核与正式重打包**：默认启用两段 CR/MR 独立审核、正式环境主干重打包（均支持在项目工作流策略按需调整，调宽高危开关给风险提示）。
- 测试/MR 打回：回到同一 `fix/` 分支开第 `N+1` 轮继续提交（使用最新版本的工作流模板与节点 Skills）。

## 3. 打包和发布（`tita` CLI）

两条命令都在**仓库根目录**执行，且 `tita release` 必须在同一目录、`tita build` 之后执行（它读本地 `dist/`）。

### `tita build`（源码）

1. 读 `package.json` 的 `name` 和 `packageManager`，用对应工具（pnpm / npm / yarn，默认 yarn）从内网 registry 装依赖；默认先删 `node_modules`，`--noRm` 不删。
2. 执行 `npm run build-prod`。**不分环境**，测试和正式打的是同一种产物，区别只在后面发到哪个 Apollo 环境。
3. 把 `dist/` 上传到 OSS 的 `ux/<name>/release/dist/`（已存在的同名文件默认跳过）。

### `tita release --app <app> --env <env>`（源码）

- 作用：**更新 Apollo 配置**，让目标环境加载这次打出来的文件。不重新打包、不上传文件。
- `--env`：`DEV` / `TEST` / `LABS` / `PROD`，默认 `TEST`。
- `--app`：`www`（Apollo 应用 `Tita_Static`）/ `okr`（`okr.tita.work`）/ `assess`（`assess.tita.work`），默认 `www`。每个项目在发布配置里选。
- `--integrity`：生成 integrity；`app=www` 时总是生成。
- 需要 `package.json` 里有 `configFile`（Apollo 里对应的配置名）。
- 版本号**不用传**：从 `dist/` 里的文件名读出版本，替换 Apollo 配置里的资源地址；同时把当前 `git rev-parse HEAD` 写进配置的 `<CommitId>`，发布标题是版本号。

### 发测试与正式环境（默认 `tita + Apollo` 预设，支持自定义多环境与策略）

- **谁能发起与审核**：测试环境发布人、测试人（默认提单人或当场选，支持配测试权限组互测）、主分支 MR 发起人、正式发布人、谁能回滚（生产与非生产均纳入 RBAC 与可配策略，「任何人」= 作用域内持对应权限成员，不写死角色名）全部支持项目配置并带内置默认值。
- **默认安全策略（均可按项目工作流开关调整）**：默认正式环境须经测试通过、合入主干并由持正式发布权限成员确认，且强制在主分支最新提交重新 `craft build`、显式锚定目标 `env_code`（如 `--env PROD`）；操作均用本人凭据（`personal_exec`）写回并查生效不倒退；回滚只回滚目标配置不重新打包。

## 4. 开工前 Bot 怎么试构建与多技术栈验证

- 通过 `ToolchainAdapter` 自动探测构建工具（支持 `pnpm / npm / yarn / bun / go / python / java` 与 Monorepo 子包 `--filter`）；前端默认优先跑 `build-prod`（无再找 `build`），绝不执行会上传线上产物的正式发布命令；后端/SDK 项目走 `verify_strategy` 跑隔离容器单测或接口探测，不强绑浏览器 `dist/`。
- 试构建与规范均支持开发者在「设置 → 项目」微调。

## 5. 跨仓库依赖（大包与多仓并发规则）

- 优先按工作区依赖图与代码探测识别跨仓拓扑，存入 `bundles / bundle_items` 拓扑表（可配任意前后 DAG 依赖，不写死固定三层）；读不出来的在工单「大包明细」标「待确认」。
- **单仓/大包部分失败与依赖升版 5 条通用规则**：① 单仓失败支持原位重修重发（勾选具体问题仓重修，不打回已生效兄弟仓）；② 上游组件改码发新版本后，已发布测试环境的下游仓**必须基于各自 `fix/` 分支升级重跑**（旧项置 `stale_needs_upgrade`），严禁从测试分支重提；③ Bot 自动生成的纯依赖升级提交（仅改 `package.json`/锁文件且过试构建）默认直进 MR 审（高合规模板可配回第 4 步）；④ 一键执行遇部分节点无权时有权仓先推进，至无权节点挂起等授权人接力；⑤ 等待兄弟仓期间已发环境被覆盖（`is-ancestor` 复检失败），阻断整包可测通知并将该仓置 `overwritten`，不改码直接从交付节点重对齐。
- **单单多仓与 `port/` 防绕测**：同单多仓在 `Round N+1` 未重改代码的仓库自动继承上轮 `head_sha`，若已在测试环境生效且未被覆盖则直接复用（不重提 0-Diff MR）；解环境分支冲突用 `port/` 分支时，合回主干前置强绑 `tested_fix_head_sha` 双锁 + 补丁谱系验证防误杀，并严禁 `port/` 反向合回 `fix/`（必要冲突修复单独 `cherry-pick` 回 `fix/` 重测）。

## 6. 账号

- 按环境登记，数量不限，同一角色可以多个。
- 每个账号有数据权限：只能查看 / 可以修改（只读账号配合浏览器局部替换防静默写护栏）。
- 凭证是密码或 Cookie；Cookie 账号不用填账号名，Bot 登录后自己识别。加密保存且不进对话上下文。

## 7. 规则（Skills）与可定制节点工作流

- 新项目开箱自带默认工作流预设模板与示例 Skills；在 **「设置 → 项目 → 流程模板」** 可增删调整节点，并**为每个 AI 节点独立挂载专属 Skills 与行为指令**。
- **打回 / 接手 / 重试的可配置回退节点（全部节点可选）**：在模板默认策略与实际打回弹窗中，下拉框均**完整列出当前工作流模板的全部节点**（默认预选模板推荐值：机审失败回最后改码节点、崩溃重启同节点续跑、代码打回/复测失败回定位与改码节点、人工接手 `self_delivery` 回交进确定性机审门禁），用户可按实际原因改选任意节点；被跳过的上游节点标为 `skipped_inherited` 沿用已有证据，一旦产生新代码 `head_sha` 则后置校验/门禁产物自动重跑。
- **Skills 五层覆盖优先级**：`底座安全边界 (P5, 不可覆盖) > 本轮人工打回/补充 (P4) > 节点专属绑定 (P3, 支持 merge 叠加 / override 替换) > 项目通用规则 (P2) > 空间/部门默认包 (P1)`；节点结束即卸载 P3 正文，防止上一节点规则污染下一阶段。
- 规则与流程版本在每轮启动时冻结；改动从 **下一轮任务（新单首轮或打回重修下轮）** 开始生效，进行中的轮次沿用启动时版本。

## 已确认（2026-11-20）

- 发测试环境用 `tita release --env TEST`，不走 `tita test-release`。
- 两次 MR 的审核人按项目设置来定。
- 两次 MR 都**单独审核**：合入测试分支的 MR 不沿用工单代码审核的结果，审核人就是修复人也要再点一次；审核通过后由工作台调用 GitLab 合入，不让人再去 GitLab 点。
- 合回主分支的 MR 不自动提：测试复测通过后，由修复人在工作台点「合回主分支」，Bot 才提 MR。
- 发测试的人是项目里的一个选项：默认工单修复人，可改成指定的人，也可以是「任何人」。
- 工单完成由工单负责人点「修复完成」，不按条件自动完成。
- 正式发布人默认「任何人」，可改；正式发布前必须测试通过。
- 一期不做 `LABS`，正式环境就是 `tita release`，不加额外配置。

## 已确认（2026-11-21）

- Apollo 账号由使用者自己在工作台里配，谁点发布 / 确认回滚就用谁的账号。`tita release`（源码）直接连 Apollo 时用的是 CLI 内置凭据、操作人固定 `deployuser`，所以工作台改为：用本人账号读出当前配置 → `tita release --local-config <目录>` 在本地生成新配置 → 用本人账号写回并发布。详见 `06-技术设计方案.md` 7.2。
