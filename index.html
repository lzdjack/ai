1. 一期要解决什么问题

测试在 Jira 报 Bug，线上问题主要经 Tita 工单管理流入。工单交给 AI 后，即使负责人关掉电脑，Bot 也应在公司内网服务器上持续工作，完成定位、修复与浏览器验证。负责人收到通知，可以直接用手机看证据、提意见、打回或通过。

沿用既有「AI 修复」流转思路，重新设计工作台。执行环境按服务器已能访问公司环境处理。以下约定用户能做什么、如何判断完成；接口、客户端框架、部署和网络验证留到技术设计。

1.1 产品参照与一期范围

产品参照为 xAI 的 Grok Bot 官方介绍，查阅于 2026-11-20。官网演示了给 Bot 分配职责、让它在自己的计算机上持续工作、在会话里交办和补充任务、教它重复使用的工作方法，以及在需要人决定时带着结果回来。这些交互在本产品里有如下具体含义，开发和验收以本表及第 7 节为准。

参照体验本产品一期行为人能看到什么
给 Bot 一份长期职责，让它主动接活Bot 按配置定期收取已交给 AI 的 Jira 或 Tita 工单。符合条件的一次交付产生一个任务，负责人关闭客户端后任务继续收单通知、来源、负责人、执行 Bot 和当前进度
Bot 拥有可操作工具的工作环境Bot 在指定内网服务器上读工单、改代码，按本轮 Skill 使用服务器浏览器操作目标页面与同一轮次关联的代码差异或 MR、实际操作、证据和未验证项；工作台可直接查看审核所需材料
在同一段对话里持续协作每张单保留自己的协作记录。负责人可从任一端补充资料；需要协助时 Bot 在原单任务里提具体问题。回答或打回后沿用已有上下文能区分负责人补充、Bot 回复、本轮是否采纳，以及还有什么需要人处理
教给 Bot 可复用的工作方法使用者创建、导入、选择编码与验证 Skills，平台可提供内置示例。只有人明确保存的经验才成为可复用规则项目能查看启用规则，审核人能回看某一轮实际采用的规则和操作；详见第 4 节
交回完成的工作，请人决定每轮交付附根因、改动、验证证据和剩余问题。修复人收到桌面或手机通知，可通过或带理由打回重修后能看到针对上轮反馈的变化；通过后保留回原平台人工确认的待办

一期聚焦 Bug 修复，内置面向工作台业务的 AI 对话入口（见 1.3）。与工作无关的通用聊天、会议助手、多 Bot 互相转派、观看演示后自动学会新 Skill 等官网能力留给后续独立评估。产品原型中的截图、角色和示例步骤只用于评审呈现，不能据此写死业务规则。

1.2 账号、开通与工单归属

已确认：PC 和手机都能处理工单，真人修复人负责审核；Tita 取「AI干活」节点负责人。Jira 收单信号已确认，真人修复人字段仍待确认。Bot 是执行者，审核和打回要记录实际操作的成员。

维护者建议，待产品负责人确认：一期采用公司身份登录、管理员开通试点成员。采用这个方案时，用户路径如下。身份入口与首批开通范围列在第 8 节，不能假定公司身份服务已经接入。

用户遇到的情况建议的产品行为
首次使用管理员开通成员及其项目范围。成员选择「使用公司账号登录」，首次成功后建立工作台身份，无需另设密码或单独注册。未开通者看见开通说明和管理员联系入口。
接收自己的工单工作台成员可以关联 Jira 与 Tita 的来源身份。收单时先确定原平台的真人修复人，再匹配工作台成员。同名、缺失或多个候选时保留工单，提示管理员处理；匹配明确后向正确成员补发通知。
日常权限成员查看获授权项目内的工单、证据和附件。通过、打回及标记原平台已确认由该单的真人修复人操作。管理员负责成员、身份映射和项目授权；管理员代审未列入一期。
手机从通知进入已登录且有权查看时直达工单。登录过期则先登录，再返回原工单；若换了账号或权限已撤销，告知当前账号无权查看，不展示工单内容。
双端同时审核同一成员在手机通过后，PC 的待办同步消失。若 PC 上仍留着旧页面，提交旧操作时显示已有审核结果，不重复打回或通知。
停用或负责人变化停用成员后停止其双端访问和新通知，已作出的审核保留署名。仍待其审核的工单列入负责人待处理清单，明确新负责人后再投递。

1.3 通过 AI 对话操作整个工作台

PC 和手机均提供全局对话入口。在首页可以跨工单提问或办事；从工单、项目或设置页进入时，对话显示当前关联的对象，并允许切换。用户在手机接续电脑上的对话时，可以看到此前选中的工单、已执行的动作和最新业务状态。对话助手代表当前用户使用软件，服务器修复 Bot 负责执行工单任务。两者通过工单及修复轮次关联。

模块设计约定：一期每个业务模块都要同时写清「人能看什么、能做什么」「如何用自然语言完成同一件事」「到哪里核对结果」。需要本人完成的登录、系统授权、原平台人工确认等动作，由对话引导到对应入口。后续新增功能也按此约定验收。

使用者说的话助手应读取的数据和执行结果
“我有哪几张待审核？先看没做浏览器验证的。”按当前成员、任务状态和最新一轮的验证记录筛选，列出来源、编号、原因和详情入口。能区分「未执行」「执行受阻」「已通过」「结果未知」。
“这张为什么又退回来了？上轮已经修了什么？”将历轮打回意见、改动、实际验证及 MR 对应到同一工单，引用具体记录。找不到证据时说明缺哪项。
“用普通员工再测一次，重点看切换第二个分组。”在当前单记录补充及发起人。处于需要协助时按状态继续；处于待审核时根据用户意图发起复测或打回。回复中区分「已提交给 Bot」「正在执行」「已有验证结果」。
“把这个验证 Skill 用到审批项目，下一轮启用。”在用户有项目设置权限时，确定项目、Skill、作用范围和生效时机，保存后给出设置入口。其他项目及历史轮次保持原有规则。
“这张我审核通过。告诉我下一步做什么。”核对当前轮次和真人修复人资格，记录该成员作出的审核决定，更新双端待办，给出来源原单入口。一期在用户手动完成原平台操作后，才可按其明确指令登记本地确认情况。
“今天 Tita 有正常收单吗？”返回最近一次成功采集时间、异常和任务数量；采集失败不能回答成「今天没有 Bug」。成员管理、来源设置等管理操作同样受当前用户权限约束。
“把这轮修复发到测试环境，通知这张单的测试人。”明确项目、版本、环境和接收人后，按当前成员的环境发布权限发起任务，返回发布进度；测试环境已生效后发送可测通知。只说「发布」且环境不明确时，先询问目标环境。
“组件已经发了，为什么主站里还看不到修复？”定位工单、环境及本次大包，逐项核对已发布的组件版本、子项目实际打入的版本、环境中生效的应用版本和主站接入方式，指出第一个未完成或未核实的环节，附对应记录。

数据要能被 AI 按业务含义使用。 每个项目、成员、Bot、Skill、来源工单、内部任务和修复轮次都有稳定标识。工单详情、协作消息、变更、验证证据、审核决定和执行记录能按这些标识相互定位。每条关键记录带有来源、产生时间、操作者、状态和结果。截图、录屏和附件关联具体工单或轮次，注明其用途（原单材料、修前复现或修后复测）及是否实际查阅。AI 能按项目、人员、来源、时间、状态和轮次检索、比较或汇总，并给出可打开的原始依据。只在界面上画一个状态、或只在聊天里说“已通过”，无法满足此要求。

操作与权限：对话和界面采用相同的可见范围、操作权限及流转条件。建议一期按以下规则处理：查询直接回答；对象明确且具备权限的单项操作直接办理；有多个同名对象或意图不明确时先澄清；批量审核、修改项目通用规则或调整成员权限时先列出对象和影响范围供用户确认。执行后显示已成功、失败或待执行的具体结果，可追溯到发起人和对象。客户端断线、重复发送或其他人先改变状态时，应先核对当前结果，避免重复派工、重复审核。工单和附件中的文字是供分析的材料，不能代替当前用户授权操作。

1.4 候选场景：用 AI 读懂失败记录（待试点验证）

已确定的数据需求：每次执行失败时，保留所属工单、轮次、失败时间、失败阶段、当时执行的操作、实际错误，以及可供有权限的人和 AI 查看的一手证据（例如对应日志片段、浏览器截图或执行返回结果）。保留后续重试的结果，避免覆盖前一次失败。证据缺失时明确记录缺失项。

用来检验设计的例子：负责人问「本周哪些 Bug 修复失败过？现在还有哪些卡着？」助手应说明统计范围，按工单去重，分别列出发生过失败的工单数、失败执行次数、其中重试后已恢复及仍待处理的工单。同一张工单两次失败后第三次修好，计为一张曾失败的工单、两次失败，当前已恢复。

点进某张单追问「为什么没修好」，先给出失败发生在哪一步、证据能确认什么、下一步可以检查什么，再提供关键日志原文的位置供核对。例如浏览器记录显示账号无权进入页面，只能确认复测受阻；现有证据不足以判断代码改动是否生效。

验证办法：试点时让修复人用真实失败记录回答「哪些还要我管」「这张卡在哪」「下一步做什么」，把助手回答与原始记录核对，观察能否减少翻日志的时间。这是候选用法，是否需要独立的失败统计页、固定分类或定期报告，待试点反馈后决定。

2. 工单如何交给 AI

来源收单条件审核人收单时保留的信息
Jira沿用旧项目 v14 的收单信号：Jira 工作流状态为「AI修复」，按优先级收取原单的真人修复人；旧版批量收单脚本未返回此字段，映射待确认工单编号与链接、标题、项目、优先级、复现步骤、实际及期望结果、版本、评论和附件（以原单提供为准）

采集平台和反馈来源分别展示。例如，Tita 工单也可能标记为「产研自测」。同一来源、同一工单的同一次交付只建一项任务，只发一次接单通知。打回后沿用原任务并保留历轮记录。

工作台分别展示两个来源最近一次成功采集时间。采集失败应可见，恢复后补收漏单。收单后若无法确定审核人或目标项目，列入需要处理的异常，说明缺少哪项信息。

「原平台确认情况」单独记录。用户在 Jira 或 Tita 完成人工操作后，可在工作台标记「我已在原单确认」。打开链接不算确认，同一张单继续被采集也不会因此再开一轮。Tita 点击「已完成」表示完成当前流程节点；是否还需复测或关闭整单，遵循原流程。审核通过也不代表已上线。

一期所有 AI 修复和审核状态在本系统流转。后续按平台接口支持情况逐步提供状态回写。

3.1 在 PC 和手机 App 内审核代码（一期必备）

修复人从「待我审核」通知进入工单，打开「代码变更」，直接审阅 Bot 本轮实际提交的代码。每轮列出关联仓库、基线提交、修复提交、变更文件和 MR 入口。一次修复涉及多个仓库时，能够逐仓查看。授权用户在外网远程接入工作台后，可在 App 内完成代码审核。

  • 看改了什么：按文件查看新增、修改、删除和重命名；逐行标明增删、行号和上下文。可以从任一改动跳到该提交中修复后的完整文件；已删除文件可查看删除前的版本。
  • PC 怎么审：左侧选择文件，右侧并排或逐行比较，可展开上下文、定位到具体一行。手机默认单列显示差异，支持切换文件、展开代码、查看完整文件，再回到原来的审核位置。
  • 怎么问和打回：选中代码行即可询问 AI「为什么改这里」，回答引用本轮文件和行号。修复人可将代码位置和意见一起提交给 Bot。重修后可切换「相对基线的全部改动」和「相对上轮的改动」，核对反馈是否解决。
  • 审核哪个版本：通过或打回时记录实际审阅的提交及轮次。若手机审阅期间出现新的修复提交，提示查看新增改动后再确认。代码未加载完整或无读取权限时，明确展示缺失范围和原因，不能把缺失的差异显示为零改动。审核通过记录真人审核结论；发布到目标环境由单独的发布动作触发（见 5.1）。

4. AI 设置与任务协作

编码和验证规则由使用者注入

工作台以 Skill 为单位管理可复用的工作规则。平台可以内置一些编码、验证 Skills 供选用；使用者也可以创建或导入自己的 Skill，在 AI 设置中查看内容、选择启用范围、替换或停用。一个项目可以分别选择编码 Skill 和验证 Skill，同一份 Skill 可以复用于多张工单。

在线编写（一期必备）。 PC 和手机的「AI 设置 → Skills」并列提供「在线新建」和「导入」。使用者可以从空白开始填写名称、用途和规则正文，也可以打开已有的自定义 Skill 继续编辑；导入的 Skill 使用同一个编辑器。内置 Skill 可复制为自己的版本再修改。

编辑中可保存草稿，稍后从另一端继续。使用者也可以请内置 AI 根据描述起草或修改规则，先检查草稿再决定是否采用。只有具备对应权限的人选择项目并确认启用后，新版本才从该项目下一轮任务开始生效。进行中的任务沿用启动时的版本，历史轮次可回看当时的规则正文。

例如，团队可以为审批项目注入编码规则「优先复用现有表单组件」，以及验证规则「按工单复现路径回归，并记录最后一次交互的结果」。Bot 根据本单材料将规则落实为具体操作。工单没有给出角色或分组名称时，Bot 应标出缺失条件；只有使用者明确保存，单次补充才成为可复用规则。

在「AI 设置」中，使用者看到的是可选和已启用的 Skills、来源（平台内置或使用者注入）及内容。在工单详情中，审核人看到的是本轮实际采用的 Skills、具体执行步骤和证据。规则发生变更后，仍可查看历史轮次当时采用的内容。

范围用户可以维护的内容
全局默认 AI 工具或模型、共用修复提示词、允许自动执行的动作、需要人工协助的条件
项目产品线、模块与仓库的对应关系，环境、业务资料与可用测试角色；为项目选择适用的编码和验证 Skills，并可用自己的规则替换内置规则
来源Jira 测试单重点采集测试版本、复现和预期；Tita 工单保留反馈来源、发生环境、受影响版本及沟通记录
单张工单修复人通过 PC 或手机补充文字、截图、录屏、操作入口或业务判断；补充和打回原因随本单保留

每一轮都能查看 Bot 实际采用的工单材料、规则和最新补充。无法判断版本或账号角色时，Bot 就这个问题请求协助。运行中收到新信息，应让修复人知道本轮是否已采纳。只有用户明确保存为项目规则的经验，才应用到其他工单。

5. 服务器执行与浏览器验证

所有 Bot 在指定公司内网服务器上全天候执行。PC、手机退出或断网不会中断修复。单张任务记录目标仓库与版本、当前阶段、交付改动或 MR、验证证据和阻塞原因。交付步骤失败时，重试应复用已完成的工作，避免重复创建修复任务或 MR。

服务器提供浏览器操作、截图和录屏能力。本轮如何复现、如何复测、采用何种证据，按使用者启用的验证 Skill 执行。平台可提供「页面交互回归」作为内置示例，要求在目标环境尝试复现，并在包含改动的版本上复测。审核页区分计划步骤、实际执行、验证结果与待确认项，注明所用环境和版本。

例如「审批中心，发起审批，点击分组界面卡住」：若启用了上述验证 Skill，Bot 可结合原单给出本轮操作，检查点击分组后能否继续交互。具体账号、分组和预期取自所选规则、工单或使用者补充。修复人可以直接在手机上看结果。

5.1 一键打包发布与人工提测

一期已确认：支持从工单在 PC 或手机发起一键发布，目标分为「测试环境」和「正式环境」。选定版本及目标后，服务器按项目发布配置完成打包、部署并检查目标环境实际生效的版本。客户端可随时关闭，再次打开能接续查看进度。

步骤使用者操作与可见结果
发测试环境在工单「发布」页看到修复轮次、提交、涉及应用、目标环境的当前版本及本次将包含的变更。选择或沿用工单测试人，点击「发布到测试环境」。如果实际发布包还包含其他工单的变更，一并列出。
通知测试人新版本在测试环境生效后，通知指定测试人。通知可直接打开测试入口，并带上工单、已部署版本、改动摘要及待复测步骤。若同一环境后来被新发布覆盖，旧通知提示当前版本已变化。
记录测试结果测试人针对实际测试的版本选择「通过」或「打回」，可附文字、截图或录屏。打回意见随原单回到修复人和 Bot；产生新提交后，上一版本的测试结果保留在历史记录中。
发正式环境提供独立的「发布到正式环境」动作，明确列出发布范围、目标版本和对应测试记录。建议默认由有正式发布权限的人发起，发布已通过人工测试的代码版本。正式环境如需按环境配置重新打包，应能追溯到相同源码及发布范围。
查看结果或重试每次发布记录发起人、工单、应用、提交与产物版本、目标环境、时间、阶段、结果及日志。分别展示打包、部署和生效检查；某一步失败时显示失败位置、已生效范围和重试入口。跨端重复点击可回到同一发布任务。

发布状态、人工测试结果、代码审核结论和原平台确认分别记录。工作台按项目配置两个环境的发布目标、入口与角色。测试人、修复人和正式发布人可以是不同成员；PC、手机和 AI 对话使用相同权限。助手能回答「这个 Bug 现在测试环境和正式环境各是什么版本」，并引用两条环境发布记录。正式发布的权限归属、是否强制人工测试通过，以及生产回退策略，留待项目评审。

5.2 跨项目大包发布与流转明细（一期）

一次修复可能横跨组件包、子项目和主站。「大包」指为交付同一项修复而一起推进的一组版本与发布步骤。它可以包含多个独立产物。修复人在工单里进入「大包明细」，能看到本轮涉及哪些仓库、为什么涉及、各自要发什么，以及最终从哪个业务入口验收。

生成发布清单。 项目维护者配置组件包的使用方、子项目的构建发布方式，以及主站如何加载该子项目。系统结合本轮代码改动和依赖关系给出建议清单，区分「改了业务代码」「需要升级依赖并发布」「只需从业务入口验证」。发布人可核对、增减范围并记录原因。其他项目即使引用同一个组件包，也只在本次修复要求它们采用新版本时进入清单。缺少依赖关系时标明待确认。

示例：组件 C 的问题影响子项目 A。 下表使用示例版本，具体项目名称和接入方式由项目维护者配置。

步骤依赖与操作该步完成的依据
1. 发布组件 C对已审核的组件修复提交打包，发布约定的新版本，例如 1.4.3记录组件提交、包名和确切版本，可供 A 获取
2. A 升级组件将 A 使用的 C 从 1.4.2 更新为 1.4.3，记录依赖变更；需要锁文件的项目同步更新锁文件可审阅 A 的依赖差异；构建实际解析到 C 1.4.3
3. 构建并发布 A使用确认过的 A 提交构建；将产物部署到本次选定的环境记录 A 的提交、产物版本及其中使用的 C 版本，核对目标环境实际生效的 A 版本
4. 主站接入并验收若主站固定引用 A 的版本，先更新引用并发布主站；若主站直接加载独立部署的 A，则从实际业务入口验证记录主站是否需要发布、入口实际加载的 A 版本、浏览器验证结果及证据。任一步缺少证据均标明未核实

一键执行与明细。 PC、手机和 AI 对话使用同一份清单。发布人可在开始前看到目标环境、各项当前版本与目标版本、先后关系、关联提交/MR；每步运行后补充实际版本、状态、时间、执行结果和日志。组件 C 被 A、B 两个本次必发子项目引用时，C 发布一次，A、B 可分别升级并发布；依赖两者的主站步骤在两者就绪后执行。

部分成功、重试与提测。 如 C 已发布、A 构建失败，大包显示「部分完成 · A 构建失败」，主站依赖步骤显示「等待 A」。重试先核对成功步骤的产物，再从失败处继续；若必须修改组件源码，应发布新的组件版本并将依赖旧版本的下游步骤重新标为待更新。多项目只完成一部分时，详情持续展示各项目当前实际生效版本。目标环境的必发步骤完成且业务入口已核实后，再发整包可测通知，通知关联本次大包版本清单。

测试与正式分别留痕。 测试结果绑定当时的组件、子项目和主站版本组合。正式发布前展示与已测清单的差异，区分环境配置或包标识变化与源码、依赖变化；后两者需重新标明受影响的审核和复测范围。正式环境的每步结果单独记录，不能沿用测试环境的「已生效」状态。

5.3 报错展示（一期必备）

收单、修复、验证、打包、部署或生效检查失败时，PC 和手机的任务详情直接展示失败步骤及工具实际返回的错误原文。错误码、退出码、文件和行号在工具有返回时一并显示。保留换行，可复制报错并展开对应这一次尝试的上下文日志；凭据等敏感值在展示、复制和 AI 引用前脱敏。若工具超时或没有返回错误文本，明确说明已观测到的情况。

发布失败时，通知相关负责人「哪个环境、哪个项目、哪一步失败」，点击直达本次错误。跨项目大包同时列出已生效、失败和等待中的步骤。AI 解释或建议单独展示，附所依据的日志位置；根因未确认时标注待核实。重试保留上一次的原始错误，方便对照。

5.4 Apollo 紧急回滚（一期移动端必备）

现场依据：公司 Apollo 配置中心的 Tita_Static 项目 按环境、集群和 Namespace 管理配置。只读查看时，在 TEST / default / application 看到了发布历史、回滚已发布配置和授权入口；该 Namespace 提示从未发布。正式环境与各子项目、静态资源配置项及历史产物的实际对应关系，实施时核对。

在家处理线上故障：值班人从手机首页「紧急回滚」、故障通知或对应发布记录进入，不要求先创建 Bug 或先启动 AI 修复。在授权远程接入下，整次操作在 App 内完成。由公司内网服务按项目授权对接 Apollo，手机不必直连内网管理页面。

  1. 选择应用及环境，展示当前生效发布、集群、Namespace、历史记录与可恢复目标。优先呈现有成功验证记录的历史版本，标明依据。若无可回滚历史、旧产物不可用或无法核实作用范围，说明具体原因。
  2. 预览当前与目标配置差异、实际会改变的应用和资源版本。按 Apollo 实际支持的粒度列明范围；若一次回退整个 Namespace 会连带恢复其他配置，列出这些变化。涉及跨项目大包时，对照第 5.2 节列出主站、子项目和依赖产物的兼容情况。
  3. 具有对应环境回滚权限的真人核对环境、当前版本、目标版本和影响范围后确认。AI 可查询、比较和准备回滚预览；正式回滚需用户明确确认此次操作。若确认时线上版本已变化，刷新差异并重新确认。断网、重复点击或切换设备时可找回同一执行记录。
  4. 分别显示请求结果、Apollo 配置回读结果和业务入口验证结果。核对实际加载的资源版本，并按项目回滚验证规则检查关键页面。配置已回退但客户端仍在加载故障版本时，显示「配置已回退，业务恢复待验证」；失败或部分生效时展示原始错误、受影响范围和待处理步骤。
  5. 手机推送最终结果，保留操作者、时间、回滚理由、前后版本和验证证据。恢复后可将该记录关联到工单，让 Bot 继续定位根因。配置回滚、代码修复与原平台确认分别留痕。

6. 双端工作台与通知

  • PC App：收件箱、待我审核、需要协助、待原平台确认；查看工单证据、代码改动与执行历史；维护 AI 和项目设置。全局快捷键截图、录屏并附到当前工单是桌面定制候选。
  • 移动 App：从通知直达工单；查看改动、复现与验证录屏；补充文字或素材、通过、打回、跳转原单。系统分享菜单接收截图或录屏是移动定制候选。
  • 通知：接到新单提醒真人修复人；需要协助时说清缺哪项信息；每轮修好后通知审核。PC 提供桌面提醒，手机在 App 未打开时也应收到提醒；错过通知仍可从待办找到任务。两端共用审核结果。
  • 公司内外使用：授权用户在公司网络、家庭 Wi-Fi、移动网络下均可使用同一 App。日常审核的体验目标是无需反复手动登录现有公司 VPN。手机能在工作台内看完审核证据；原平台暂不可达时，保留人工确认待办。Tailscale 是远程访问候选，具体接入方式在实施阶段确定。

7. 一期验收场景

主场景：关掉电脑仍能交付一张可审的工单。 负责人下班关闭 PC。Tita 工单进入「AI干活」，手机收到一次接单提醒。Bot 按项目启用的 Skills 开始处理；发现缺少复现角色后，在此任务内提问。负责人在手机回复「用普通员工」；Bot 在服务器浏览器按该角色操作，交回改动和实际验证证据。负责人打开通知查看本轮材料，打回并说明另一个分组仍有问题。Bot 保留首轮记录，修订后再次交付。负责人通过，PC 同步结果，工作台保留待回 Tita 确认的事项。各动作都能从同一张单追溯。

场景可观察的通过条件
用手机对话完成审核修复人询问「还有哪张没复测」，点开回答引用的证据，要求某张单按补充条件重测。Bot 接到一次任务，PC 能看到同一轮次和发起人；在结果产生前，对话显示待执行或执行中。
权限与状态一致无权成员通过对话查询其他项目时看不到工单或附件，也不能代他人审核。已通过的任务收到旧会话里的打回指令时，提示最新状态，不静默改写原决定。
通过对话调整项目规则有权限的用户确认项目与 Skill 后启用规则，设置页能看到同一变更。下一轮展示实际采用的规则，历史轮次可回溯。
Jira 收单把一张测试 Bug 交给 AI，出现一项任务，真人修复人收到通知。连续采集不会重复开工。
Tita 收单工单整体为「解决中」且「AI干活」节点进行中时收单，通知节点负责人。只满足整体状态时不收单。
人离开电脑电脑关机后 Bot 继续工作；负责人在家用手机补充测试角色，Bot 接续原任务并展示采用的条件。
使用者注入 Skills使用者为项目启用自定义编码 Skill，用自己的验证 Skill 替换内置示例。下一轮按选定规则写代码和验证；审核人能查看两份规则的来源、当轮内容、对应改动与验证结果。
在线编写 Skill在 PC 在线新建验证 Skill 并保存草稿，手机可打开并续写。保存草稿后 Bot 仍沿用当前规则；确认在指定项目启用后，下一轮采用新版本，上一轮仍能查看原版本。
浏览器复测审核人能辨认改动版本、复测步骤和结果；证据缺失时看到原因，不能把仅构建成功显示成页面验证通过。
手机审代码负责人在家庭网络从通知进入「代码变更」，在 App 内查看逐行差异和修复提交的完整文件，选中一行打回。PC 同步显示该行与意见。重修后手机能单看相对上轮的改动，审核通过记录对应的新提交。
一键提测与上线修复人在手机选择本轮提交发测试。测试人从可测通知进入指定环境，记录该版本的复测结果。获正式发布权限的成员选择已测版本上线，工单中可核对两个环境分别生效的版本、发起人和时间。
跨项目大包与断点续发同一组件供 A、B 使用，两者本次均须发布。组件发包成功、A 成功、B 失败时，手机可看到三个实际结果、B 的失败原因及主站等待项。修复并重试 B 后核对 A、B 使用的组件版本和主站实际加载的版本，才发出整包提测通知；历史清单和各次尝试可追溯。
发布失败与重复操作模拟打包通过但部署失败，界面显示部署失败及证据，测试人不会收到「可测」通知。重试成功后通知一次；旧客户端重复提交不会再次部署同一任务。
报错可定位子项目 A 构建返回带文件、行号的错误时，负责人从手机通知直达该次构建，能复制实际报错、展开日志，并看到主站在等待 A。在 PC 或 AI 对话中查看同一次失败时，错误与界面一致。
在家用手机紧急回滚全程关闭 PC。值班人从手机选择正式环境发布，看到配置差异和受影响应用，确认后退出 App。再次进入可查看同一回滚结果、实际生效版本及业务验证；仅配置成功时不宣告故障已恢复。无权限成员只能看到其权限允许的信息。
手机打回与再审手机打回后 PC 同步状态；Bot 读取反馈，保留两轮差异，重新通知同一人。通过后仅保留一次待原平台确认。
平台人工确认用户可跳回来源平台、完成对应操作并回来标记；系统能区分审核通过、已打开链接和用户已确认。
网络或采集恢复手机从内网切到移动网络后能继续审核同一任务；来源采集短暂失败可见，恢复后漏单可补、已有任务不重复。
账号开通与回跳（按建议方案评审）已开通成员首次登录后可见授权项目；未开通者看到开通说明。同一人手机登录过期时，点通知并重新登录后回到原工单。
身份和审核权限（按建议方案评审）两名同名成员不会因显示名相同收到彼此的审核任务。映射待处理时保留工单；确认归属后通知正确成员。非修复人无权代审，停用成员无法通过旧通知继续访问。

8. 下轮评审待定

  1. Jira 从哪个字段取得真人修复人；Tita 节点多人负责时谁有权作最终审核。
  2. 首批支持哪些桌面和手机操作系统；桌面快捷录屏、手机系统分享是否进入首发。
  3. 新单采集和通知的可接受时延，以及可同时处理的工单数和优先级顺序。
  4. 首批试点项目、仓库、测试角色和典型验收用例；哪些问题允许带着「待人工复测」提交审核。
  5. 是否采用第 1.2 节的公司身份登录和试点开通方案；由谁管理成员、项目访问范围及来源身份映射。登录服务与通知通道的接口在产品选择确认后进入技术设计。
  6. 每个项目的测试人默认如何选定，谁有正式发布权限；人工复测、合并及发布的先后要求，正式环境回退方式。
  7. 用一条真实的「组件包 → 子项目 → 主站」链路评审大包清单，确认主站如何取到新版本、测试包如何对应正式包，以及多项目部分上线时团队采用何种回退顺序。

3. 打包和发布（tita CLI）

两条命令都在仓库根目录执行，且 tita release 必须在同一目录、tita build 之后执行（它读本地 dist/）。

tita build（源码）

  1. 读 package.json 的 name 和 packageManager，用对应工具（pnpm / npm / yarn，默认 yarn）从内网 registry 装依赖；默认先删 node_modules，--noRm 不删。
  2. 执行 npm run build-prod。不分环境，测试和正式打的是同一种产物，区别只在后面发到哪个 Apollo 环境。
  3. 把 dist/ 上传到 OSS 的 ux/<name>/release/dist/（已存在的同名文件默认跳过）。

tita release --app <app> --env <env>（源码）

  • 作用：更新 Apollo 配置，让目标环境加载这次打出来的文件。不重新打包、不上传文件。
  • --env：DEV / TEST / LABS / PROD，默认 TEST。
  • --app：www（Apollo 应用 Tita_Static）/ okr（okr.tita.work）/ assess（assess.tita.work），默认 www。每个项目在发布配置里选。
  • --integrity：生成 integrity；app=www 时总是生成。
  • 需要 package.json 里有 configFile（Apollo 里对应的配置名）。
  • 版本号不用传：从 dist/ 里的文件名读出版本，替换 Apollo 配置里的资源地址；同时把当前 git rev-parse HEAD 写进配置的 <CommitId>，发布标题是版本号。

发测试环境

谁能发：项目里的「发测试的人」，默认工单修复人，可改成指定的人或「任何人」。

直接 tita release --env TEST。不用 tita test-release（提测版本），用户已确认那条路不对。

发正式环境

  • 必须测试通过才能发正式，没通过的版本界面上不给发。
  • 正式发布人是项目里的一个选项，默认「任何人」（有工作台权限的项目成员都能发），可以改成指定的人。
  • 谁能紧急回滚也是项目里的一个选项，默认同正式发布人，可以改成指定的人；测试环境回滚不限（2026-11-21 用户确认）。
  • Jira 单的测试人默认是提单人，发测试前可以换；提单人不在工作台或已停用时必须选一个才能发（2026-11-21 用户确认）。
  • 正式环境就是 tita release 加 --env PROD，不需要另外的配置。注意：源码里 --env 默认是 TEST，所以 Bot 执行正式发布时必须显式带 --env PROD。
  • 一期只有测试和正式两个发布目标，不做 LABS。

发完怎么确认生效

对话助手全局 AI 和本单 AI：理解用户的话，调用接口服务完成查询和操作，权限和界面完全一样支线「AI 助手」「本单 AI」不绕过接口服务直接改数据
证据与附件存储截图、录屏、日志片段、原单附件、导入的 Skill 文件；按工单和轮次归档，注明用途和是否查阅过第 3、4、9 步不存凭据

为什么 Bot 执行器和发布执行器要单独起进程：

  • 它们会在服务器上执行任意命令（AI 改的代码、构建脚本、tita CLI），出错或卡死不能拖垮接口服务。
  • 每个 Bot 一个独立的工作目录和浏览器实例，修完或超时就清理，互相看不到对方的代码和登录态。
  • 发布执行器手里有 OSS、Apollo 的发布权限，Bot 执行器没有。AI 改出来的代码即使有问题，也碰不到发布凭据（见第 10 节）。

2.1 总原则

  • 四条记录分表存：工单状态、发布任务、测试记录、原平台确认各是各的表，互不代替（链路文档第二节）。例如「审核通过」不会顺手把发布任务改成已生效。
  • 库里只放业务数据和短文本：截图、录屏、日志全文、原单附件放证据存储，表里只存对象地址和摘要。
  • 编号两套：主键用 UUID；界面上看到的编号（TK-20871、KQ-118、R-0418）是单独的字段。
  • 时间一律存带时区的时间（UTC），客户端按本地时区显示。
  • 会被多人改的表都带 rev（整数，每改一次加一）：用来防并发覆盖（第 3 节），也用来断线后按版本补齐（第 11 节）。
  • 历史不删：审核结果、测试记录、发布步骤、事件记录只追加不改；人员停用、项目下线用状态字段，不物理删除，保证「每一步都能从这张单追溯」。
  • 开始时定版本：一轮修复开始时记下用的 Skills 版本和项目配置版本，进行中的单沿用开始时的版本；改配置从下一张单生效。

3.5 多人、多设备同时操作

每个改状态的请求都带两样东西：

  • 这次点击的操作 ID：客户端每次点按钮生成一个，网络重发时带同一个。服务端记 24 小时，同一个操作 ID 直接返回第一次的结果。

3.6 改状态和外部操作分开做

合 MR、tita build、改 Apollo 这些外部操作做了就撤不回，所以不在接口请求里直接做：

  1. 接口服务在一个数据库事务里：检查前置、改业务状态、写事件记录、往队列里放一个任务。事务失败就什么都没发生。
  2. 执行器从队列取任务去做外部操作，做完再开一个事务写结果。
  3. 同一个发布任务、同一张单的修复，在队列里按对象加单例锁，同一时刻只有一个执行者。
  4. 执行器定时报心跳；超过时限（推荐 2 分钟）没心跳就算中断，按 3.2、3.3 的规则处理。

队列也在 PostgreSQL 里，所以第 1 步的「改状态 + 放任务」天然在同一个事务，不会出现状态改了任务没放进去的情况。

3.7 实时推送和断线补齐

  • events 表的自增序号就是全局顺序。每条事件提交后，接口服务通过 WebSocket 推给有权限看的在线客户端：{序号, 对象, 新版本号, 摘要}。
  • 客户端记住收到的最后一个序号。断线重连时带上它，服务端把之后的事件按权限补发；落后太多（推荐：超过 7 天或 1000 条）就让客户端整页重新拉。
  • 推送只是「提醒客户端去更新」，按钮能不能点、点了是否生效都以服务端为准。
  • 手机系统推送（APNs / 安卓推送）可能丢、可能晚到，只用来叫人；点开通知后一律向服务端拉最新状态，例如通知说「待我审核」，点开时已经被别人审了，就显示已有结果。

4.6 排队和派单

排队顺序（固定，不能拖）：

  1. 优先级：P1 最先；
  2. 同一优先级里，打回重修的轮次排在新单前面；
  3. 再按入队时间先后（打回的轮次以打回时间为入队时间）。

派单：

  • 触发时机：新建一轮、某个 Bot 空出来、「同时修几张」被调大、项目开工。另外每 30 秒兜底检查一次。
  • 在一个事务里：数正在修的轮数，还能修几张；按上面的顺序锁住排在最前的几轮（跳过已被别的派单锁住的）；改成「修复中」；往队列里放执行任务。并发派单也不会多派、重派。
  • 「同时修几张」调小时不打断正在修的，只是空出来以后少派。
  • 「5 分钟内开始修」的意思是有空闲 Bot 时：采集间隔 2 分钟，派单是即时的，最慢 2 分多钟开始。Bot 都忙时就排队，界面显示排第几、前面是哪几张。

预计开始时间（界面上的「预计 15:40 开始」）：用最近 20 轮的平均用时，加上正在修的几轮已经用掉的时间，粗算出最早空出来的时间。只当参考，写「预计」。

多租户两级公平调度（当多租户共享同一执行池时，专治「吵闹邻居」）：

  • 外层（租户间 Fair Round-Robin + 弹性借用）：每个租户配置保底并发 min_concurrency 与弹性上限 max_concurrency（按 tenant_quotas 套餐）。池空闲时单租户可弹性借用多余槽位；一旦其他租户有待修单，调度器优先挑选「当前运行数最少」的等待租户派单，不让大户饿死小户。
  • 内层（单租户内部）：严格沿用上方固定排序（P1 优先 → 同级打回重修在前 → 先来先到）。
  • 重资源槽位同样公平轮转：浏览器槽、试构建槽、转码槽按租户轮转借用，并配单轮硬超时（默认 15～20 分钟，构建 5 分钟，浏览器 3 分钟），超时强杀回收。

发布不和修复抢 Bot：发布任务走发布执行器自己的队列。同一个 Apollo 应用 + 环境同时只跑一个发布，后来的显示「排队中 · 等 R-0417 发完」。细节见第 7 节。

只读账号写保护（不一刀切拦 POST）鉴于大量业务系统的查询/列表/检索接口也走 POST，绝不在网络层一刀切拦截 POST，改用三层务实防线：<br>1. 优先依靠目标系统自身账号权限（正式环境推荐登记本身即只读的角色账号）；<br>2. UI 交互层写动作守卫：登录标为「只能查看」的账号时，允许自由浏览、筛选、搜索、翻页、展开详情；但 browser_action 在执行点击/提交前会校验控件语义（如「提交 / 保存 / 删除 / 通过 / 拒绝 / 作废 / 发布」或表单提交），命中即在点击前拦截返回 READ_ONLY_MUTATION_BLOCKED，转人工确认或标「待人工复测」；<br>3. 项目级可选黑名单（非默认）：仅在项目明确配置危险接口黑名单路径（如 */delete*、*/approve*）时追加网络层阻断
验证码 / 2FA / Cookie 过期严禁尝试绕过验证码；检测到登录失败、图形/短信验证码或 Cookie 过期时，立即截当前页面图并返回 AUTH_REQUIRED → 触发橙色 ask_user 卡片，引导用户更新 Cookie 或点「我来人工复现」补证据，绝不死循环
网络防 SSRF浏览器容器仅允许访问项目登记的环境域名与内网静态资源 CDN，禁止访问云元数据地址（169.254.169.254）与宿主机内网敏感管理端口

5.3 隔离：代码容器与浏览器分离，AI 改的代码碰不到任何凭据

Bot 会在服务器上运行 AI 改过的代码（装依赖脚本、构建脚本），按「代码容器完全不可信」设计，并将浏览器与代码容器物理分离（避免恶意或异常构建脚本扫本地进程 / CDP 端口窃取注入进浏览器的 Cookie）：

  • 拉代码、推分支由执行器做：执行器在容器外 clone 好代码挂进去，交付时再由执行器推送。代码容器里没有 GitLab 令牌。
  • AI 令牌不进容器：引擎跑在代码容器里，请求发往执行器的本地 HTTP Proxy，由宿主机转发层加上令牌发往模型网关。

  • 单向产物传递：代码容器试构建完成后，产物输出到只读共享卷给浏览器池做静态资源替换，反向隔离。

  • 依赖缓存按包管理器各放一个缓存目录，加快安装；多租户模式下按 tenant_id 严格分目录隔离（见 5.3a）。

5.4 怎么调用 AI 引擎（默认内置 Pi 内核 + 多模型）

默认内置 Pi 轻量执行引擎（pi-mono：pi-ai + pi-agent-core + pi-coding-agent，2026-11-24 确认），通过 pi-ai 统一适配 OpenAI 兼容网关（如公司网关 gpt-6.2-sol、DeepSeek、Qwen、GLM、OpenRouter、Ollama）、Anthropic 与 Google Gemini，不预装、不绑定任何重型第三方 CLI。执行器与引擎之间保持极薄的 AgentRuntimeAdapter 接口，详细协议与 UI 渲染映射见 第 11 节。

5.5 运行中补充资料

  • 修复人在本单 AI 里补充时，消息先存进 messages，状态「已提交给 Bot」。
  • 执行器通过 Pi 原生 session.steer() 在当前正在跑的工具调用结束后立即把补充注入上下文（同时附带 messageId 和采纳回执要求），无需等整轮或下一个人工里程碑；不打断、不重新开始，上一步做到哪就从哪继续。

5.9 Skills 加载治理与防 Token 膨胀已确认 2026-11-23

为了避免 Skills 长期积累导致单轮提示词 Token 爆炸、规则互相打架并稀释模型注意力，Skills 按「有预算上限 + 按需加载 + 有进有出」治理，设四道闸门：

闸门规则目的
1. 严进（准入）偶发细节（单点漏判空、拼写错）不沉淀；仅当审核人打回时主动勾选「存为项目规则」，或系统检测到同类打回出现 ≥ 2 次时才生成草稿，且需项目负责人确认后才启用防止垃圾碎片进入规则库
2. 懒加载（按需）分两层：常驻红线（每项目限 3～5 条核心规则，硬顶配额 ≤ 1,500 tokens）；场景规则（提示词里只放「一句话摘要 + 适用范围」，每条 < 20 tokens，Bot 定位到命中仓库/目录/模块时再调用工具按需读取正文）就算项目有 50 条规则，单轮实际进上下文也只读命中的 2～3 条，单轮 Skills 稳控在 2,000～3,000 tokens 内
3. 合并（去重）新提炼或导入的规则若与现有 Skill 属于同一模块/主题，默认建议合并修订为已有 Skill 的新版本（复用 PC-Skills-导入 的相似合并机制），不碎片化新建保持规则树紧凑、避免规则冲突
4. 淘汰（度量）依托 rounds 已记录的每轮所用 Skills 版本，统计近 60 天命中次数与启用后同类打回率变化；长期 0 命中或架构已变更过时的规则自动标「建议归档/精简」，由负责人一键下线有进有出，总 Token 长期封顶

分期节奏：

  • 一期先落底座：skills 表增加加载模式（常驻 / 按需）、适用范围（仓库 / 路径 glob / 模块）与估算 token 数；Bot 执行器实现两层加载（常驻 + MCP 按需读取正文），并在 Skills 页提示常驻配额。
  • 二期补自动化：打回频次聚类自动生成草稿、60 天零命中归档提醒。

6. 代码审核与 MR已确认 2026-11-21

对应链路第 4 步（审核代码）、第 6 步（MR → 测试分支）、第 10 步（MR → 主分支）。三次审核各审各的，结果互不沿用。

6.1 GitLab 账号和令牌

合入 MR 用审核人本人的 GitLab 账号（用户确认 2026-11-21）：每个人在「设置 → 我的账号」配自己的 GitLab 个人访问令牌（权限 api），谁点「通过并合入」就用谁的令牌合，GitLab 里记的合入人是本人，GitLab 的分支保护照样生效。没配的人「通过并合入」按钮不能点。

其余操作用管理员开好的 bot-fix 账号（令牌由管理员在「设置 → 全局 AI」的「Bot 用的账号」里配），按「谁用什么就只给什么」分三个令牌：

谁用令牌用来做什么
Bot 执行器bot-fix，只能 git 推拉（write_repository），不能调接口拉代码、推 fix/ 分支
发布执行器bot-fix，能调接口（api）提 MR、在 MR 下留言、读 MR 状态
发布执行器审核人本人的令牌合入 MR
接口服务bot-fix，只读（read_api）给审核页取改动、取完整文件

GitLab 仓库里配合设置：

  • 主分支、测试分支设保护：谁都不能直接推，只有被允许的人能「合入」（审核人要在 GitLab 里有这个权限）。bot-fix 不给合入权限。
  • fix/* 分支不允许强推：Bot 只能往后加提交，不改历史，这样「相对上轮」的比较一直有效。
  • 仓库有没有开 GitLab 自带的审批规则、是否要求流水线通过才能合，待定。开了的话，工作台合入前要先满足它，否则合不进去。

6.2 审核代码（第 4 步）

改动从哪来：接口服务调 GitLab 的比较接口取改动，按「起点提交 → 交付提交」逐仓库取。

  • 同一对提交的改动不会变，取过一次就缓存起来。手机上切文件、来回看不用每次都去 GitLab 取。
  • 「相对上轮」= 上一轮交付提交 → 这一轮交付提交。
  • 「看完整文件」= 取交付提交时的那个文件；删掉的文件取起点提交时的版本。
  • 没取全不能显示成没改：文件太大、二进制文件、GitLab 超时，都要在那个文件上写明「没加载：原因」，按钮「重新加载」。
  • 能不能看由工作台的项目权限决定，不看 GitLab 上这个人有没有权限（大家都通过 bot-fix 的只读令牌看）。

选中一行问 AI：客户端把「仓库、提交、文件、行号范围」交给本单 AI，回答里引用的文件和行号能点回去。

打回：存进 reviews 的有：意见、代码位置（仓库、提交、文件、行号范围）、截图。下一轮开始时这些原样交给 Bot（5.4），交付时 Bot 要逐条回应（5.7）。

通过：请求里带上审核的提交号，按 3.5 的规则检查（提交号是最新的、有未测项时勾了确认）。

6.3 MR → 测试分支（第 6 步）

什么时候提：

  • 全局 AI 里勾了「提 MR 到测试分支」时（推荐）：Bot 交付时就提一个草稿 MR，交付卡上的「MR」入口指向它，方便有人想在 GitLab 里看。第 6 步直接用这个 MR，把草稿标记去掉。
  • 没勾时：第 6 步点「发布到测试环境」以后才提。
  • 同一张单、同一仓库、同一方向，同时只有一个没关闭的 MR。打回后再交付，继续用这个 MR，新的提交会自动出现在里面。

审核：

  • 审核人按项目设置（默认工单修复人）。单独审核：哪怕审核人就是修复人、提交和第 4 步一样，也要再点一次。
  • 审核页和 PC-合回主分支-MR审核 是同一套：看 MR 的改动，再点通过或打回。

合入：

  • 发布执行器用审核人本人的令牌调 GitLab 合入接口，带上审核时看到的提交号。GitLab 发现 MR 的最新提交和这个号对不上会拒绝合入，所以「审的」和「合的」一定是同一份代码。
  • 不压缩成一个提交：保留 Bot 的每个提交，方便追溯。
  • 合入后记下合入提交号，然后进入打包（第 7 步）。
  • 在 GitLab 的 MR 下留一条言：「已由林某在工作台审核通过（提交 a3f9c21）」，在 GitLab 里看也知道是谁审的。

6.4 MR → 主分支（第 10 步）

  • 修复人在复测通过后点「合回主分支」，发布执行器才提 MR（fix/<单号> → 主分支），同时建正式发布任务（3.3）。
  • 审核页上的「和测试时比」分两块：
  • 本单的代码有没有变：比较「测试时合入的 fix/ 提交」和「现在 MR 的最新提交」。不一样就不让提，提示代码变了要重新测试。
  • 正式环境还会带上谁的提交：主分支上从正式环境当前版本（Apollo PROD 的 <CommitId>）到现在的提交，逐条列出作者和说明。这些是别人已经合进主分支、还没发正式的改动，这次发布会一起带上去。
  • 合入方式和 6.3 一样：带提交号合入、不压缩、留言。

6.5 合并冲突

和测试分支冲突（测试分支上有别人还没上线的改动）：

  • 绝不把测试分支合进 fix/ 分支。合进去的话，别人没测完的代码会跟着这张单进主分支、上正式。
  • 推荐和公司现在的做法一样（跨分支交付时建 port/ 分支）：从 fix/<单号> 拉出 port/<单号>-<测试分支>，Bot 在这个分支上把测试分支合进来、解决冲突，MR 从 port/ 分支提到测试分支。
  • 审核页多一块「解决冲突改了什么」，单独标出来给审核人看。
  • fix/ 分支保持干净，之后合回主分支用的还是它。

和主分支冲突（第 10 步，主分支在修复期间被别人改了同一处）：

  • Bot 把主分支合进 fix/ 分支、解决冲突，这算本单代码变了。推荐按新的一轮走，起因写「和主分支冲突」，重新走审核 → 发测试 → 复测。
  • 理由是和规则「代码变了就要重新测试」一致，不开例外。

GitLab 显示可以合，但合入时失败（别人刚好先合了一个冲突的改动）：这一步标失败，写清 GitLab 返回的原因，按上面两种情况处理后再点重试。

7. 发布、回滚与可选动态模块扩展架构已确认 2026-11-24

7.1 craft 标准指令槽与三级精细化命令映射（0 代码适配任意客户）

云匠正式定义极简零冲突 CLI 前缀 craft（避开 Unix 系统 C 编译器 cc），内置 5 个标准生命周期指令槽：

标准指令槽职责说明
craft try-build修代码后试构建（不上传产物）仅验证编译通过并产出本地 dist/ 供浏览器替换自测
craft build发布打包（上传产物包）如公司试点 tita build 或客户自研 kehu build
craft release --env <ENV>发布到目标环境如 tita release --app {{app}} --env {{env}} / kehu deploy

三级继承覆盖（越细越优先，专治不规范项目命令五花八门）：

真实企业里往往同一个公司下，仓库 A 用 pnpm build、仓库 B 用 pnpm build-prod、仓库 C 用 yarn build:test。云匠支持三级精细化映射，缺哪一层自动继承上一层：

1. 租户 / 全局默认命令（Tenant Default）       ← 规范大公司配一次全通
   └── 2. 项目级覆盖（Project Override）       ← 按业务线覆盖
         └── 3. 仓库 × 环境级覆盖（Repo × Env） ← 最精细：精确到每个仓库、TEST/PROD 环境单独指定！
  • 配置方式：支持在云匠项目/仓库配置界面直接填（Bot 接入仓库时自动读取 package.json 推测试构建命令），也支持仓库根目录声明 cloudcraft.yaml（以配置优先级明确界定）。
  • 标准化结果契约：客户命令只需按标准退出码（0 成功 / 非 0 失败）并在 stdout 末行输出可选 JSON（如 {"version":"2.18.0","commit":"a3f9c21"}），云匠的 5 步发布状态机、日志脱敏、失败断点重试、AI 报错解读即可全部自动接管。

7.3 发布执行器调度、隔离与 4C 8G 共享构建槽

  • 单应用 + 环境串行锁：同一个应用 + 环境（如 www 的 TEST）同时只跑 1 个发布任务，后来的排队并显示「排队中 · 等 R-0417 发完」；不同应用、不同环境可并行。

11.4 多包插件化隔离：Pi 与外部 CLI 同级平等，零污染核心

所有代码修复执行引擎——包括默认使用的 Pi 与未来可选的外部 CLI（ACP / Claude Code / Codex 等）——在架构上完全同级平等，全部作为独立插件包放在 plugins/ 下，统一实现 packages/core-protocol 定义的同一套 AgentRuntimePlugin API。区别只在于交付节奏：一期先做并默认启用 plugins/runtime-pi，后续按需扩展同级外部插件。

这样设计有两个直接收益：① 一期即用 runtime-pi 实战检验 AgentRuntimePlugin 契约是否完备（连 Pi 自己都不走任何后门）；② 核心代码对具体引擎完全盲视、零污染，哪怕未来把 Pi 换成更新的引擎、或删掉某个外部插件包，核心系统一行代码都不用改。

12.3 模块间通信与数据共享边界（以 ticketId 为主线，零直连数据库）

模块之间严禁互相 import 代码或直连对方数据库，全部经由内核「事件总线 + /v1/ 语义化 Host API」通信：

  1. 核心 → 模块（事件广播，PostgreSQL Outbox）：核心在业务节点落库同事务写入标准事件（如 ticket.code_approved、test.passed、ticket.reworked），附带 { ticketId, repo, branch, commitSha, actor }，订阅模块经 Webhook 或内网 cloudcraft-runner 异步接收。
  2. 模块 → 核心（/v1/ 语义化 Host API，严控暴露面）：
分类✅ 允许暴露（带 /v1/ 版本 + 最小权限授权）❌ 严禁暴露（永远锁在内核私有）
只读核心数据tickets:read、git:read_diff、projects:read、members:read（永远读唯一真相源）明文密码 / Cookie / Token / 解密私钥（只由宿主或 Runner 内存代发）
高语义写意图tickets.postCard（插对话卡）、tickets.triggerRework（打回重修，内核自动记审计）、tickets.setBadge（更新模块徽章）、notify.send（受免打扰控制）直接改底层状态枚举（防绕过审核前置与状态机）、直接写 reviews / events 审计表（防伪造留痕）
沙箱存储与执行storage.put/get/query（仅读写本模块隔离的 module_records）、runner.exec（受控命令执行）直连 PostgreSQL、ALTER TABLE 改主库结构、跨模块跨租户读数据
  1. 三层数据共享归属： - 云匠核心数据：通过授权只读 GET /host/* 共享，不乱拷贝； - 模块私有数据：二选一——① 存入云匠统一沙箱表 module_records(tenant_id, module_id, ticket_id, entity_type, data JSONB, updated_at)（天然双层隔离、随云端备份、换 Runner 0 丢数）；② 或留在客户公司自己原有数据库，只保留 ticketId 外键关联； - 跨模块摘要与 AI 检索：模块通过 tickets.setBadge 写状态徽章给工单右栏展示，并通过标准 MCP Tool 暴露查询能力，让全局 AI 助手可直接回答任意自定义模块的实时状态（如「TK-20871 现在灰度到多少了？」）。
  2. 故障隔离：任何外部模块崩溃或视图超过 5 秒超时，仅在对应插座内显示「模块暂时不可用 · 重试」，绝不拖垮核心修 Bug 主流程。
